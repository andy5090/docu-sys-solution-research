# Milvus 프로덕션 마이그레이션 및 검색 최적화 계획서

기준일: **2026-09-18**. 사용자 확인: **임베딩 대상 약 61,000여 문서, 7,585,436개 청크의 임베딩 완료**. 기존 기록의 약 95GB는 DeDRM 완료 파일 크기이며 Milvus 적재 용량과 같지 않다. 프로덕션 이관·메타데이터 보강·성능 검증은 남은 작업이다.

이 문서는 [전체 설계안](GHeSS_솔루션_재설계.md)의 후속 실행 계획이다. 실제 서버에 접속하거나 컬렉션을 변경한 결과가 아니다. **임베딩 모델 BGE-M3, 현재 유사도 척도 COSINE, 총 청크 수 7,585,436개는 사용자 확인**됐다. 실제 벡터 필드 dtype·Milvus 버전·장비 사양은 아직 미확인이다. 아래 HNSW 설정값과 합격선은 **실험 제안**이다. 공식 문서는 기준일에 확인했으며, 기능 지원은 도입할 서버와 SDK의 정확한 버전에 맞춰 재확인한다.

## 1. 이번 단계의 결론

**메타데이터 구조를 먼저 정하고, 기존 벡터를 새 프로덕션 컬렉션으로 이관한 뒤 인덱스·검색을 검증하여 전환한다.** 임베딩 입력·모델이 그대로이면 벡터를 재계산할 필요가 없다. 데이터 복사와 인덱스 재생성에 필요한 시간·자원은 별도로 든다.

| 우선순위 | 작업 | 결과물 |
|---|---|---|
| P0 | 7,585,436개 청크와 원본 컬렉션의 실제 벡터 현황 대사 | 이관 기준 manifest: 대상 목록·PK·건수·해시·처리 버전 |
| P0 | 원본 서버에서 문서·개정·출처·권한 매핑과 메타데이터 구조 개편 | 필드 매핑표, 누락/격리 목록, 새 원본 컬렉션 |
| P0 | 검증한 새 컬렉션을 프로덕션 서버에 컬렉션 단위로 복원 | 기존 벡터와 메타를 보존한 프로덕션 컬렉션 |
| P1 | 현재 인덱스와 HNSW, 필터, 샤드 1/2개 비교 | 동일 데이터·질의의 품질/지연/RAM 비교표 |
| P1 | 증분 변경을 따라잡고 단계적으로 검색 연결 전환 | 전환 기록, 복귀 시험 결과 |
| P2 | 키워드 병합·중복 억제·선택적 재랭킹·압축 등 | 확인된 병목 또는 품질 결함별 개선 |

**61,000문서와 7,585,436벡터는 다른 수량이다.** 문서당 평균 청크 수는 약 **124.35개**다. BGE-M3 표준 dense 출력인 1,024차원과 Milvus `FLOAT_VECTOR`(float32)를 가정하면 원시 벡터만 `7,585,436 × 1,024 × 4` = **31,069,945,856바이트(약 28.94GiB)**다. 이는 HNSW·scalar·세그먼트·복제본·프로세스 여유를 제외한 값이므로 실제 schema와 load 메모리를 측정해 보정한다. [BGE-M3 모델 카드](https://huggingface.co/BAAI/bge-m3), [산정 방법](트래픽_리소스_산정.md#4-milvus-메모리와-저장소).

## 2. 이관 전에 확정할 환경과 데이터

| 확인 대상 | 기록할 값 | 결정에 쓰는 곳 |
|---|---|---|
| 서버/클라이언트 | 원본·대상 Milvus 정확한 버전, PyMilvus 버전, Standalone/Distributed | 이관 도구 호환성, 스키마 변경·부분 갱신 지원 |
| 배포/스토리지 | QueryNode 등 역할별 수, CPU·RAM, 로컬 SSD/NVMe, 객체 저장소, 네트워크 | 메모리 적재 가능 여부, 복제, 이관·색인 시간 |
| 컬렉션 | DB/컬렉션명, schema, PK 타입·AutoID, 동적 필드, 샤드/파티션, consistency·TTL | 누락 없이 복제할 계약, 재구성 범위 |
| 벡터 | BGE-M3·COSINE 확인; 실제 행 수/유효 PK 수, 모델 리비전·차원·dtype·정규화·입력 prefix 확인 | 벡터 재사용 가능 여부, 질의 임베딩과의 일치 |
| 색인/검색 | 인덱스 종류·파라미터·진행 상태, load/replica, growing/sealed 세그먼트 분포 | 현재 기준선, 작은 세그먼트·미색인 데이터의 영향 |
| 데이터 품질 | 문서·개정별 청크 수, 본문/OCR 구분, 중복 PK·잘못된 벡터·출처 누락 | 복사 검증, 격리와 선택적 수정 범위 |
| 변경 유입 | 신규·개정·삭제·권한 변경 빈도, 중지 가능한 적재 구간, 변경 이력 보존 | 일관된 복사 기준점, 최종 증분 반영·복귀 |
| 검색 요구 | 실제 필터·topK, 피크 검색 QPS, 최신성·가용성 요구 | 인덱스·샤드·복제본·캐시 선택 |

행 수는 `num_entities`만 읽어 확정하지 않는다. 같은 복사 기준점에서 PK와 문서/개정별 집계를 대조하고 삭제·이력·중복·격리를 구분한다. 임베딩 완료 배치와 Milvus 적재/검색 가능 상태도 각각 확인한다.

완료 manifest에는 정확한 대상 건수와 `document_id → revision_id → chunk_id/PK` 연결을 남긴다. 원본 벡터와 청크 텍스트를 재추출할 수 있는지도 확인한다. 파싱/OCR 산출물에 없는 페이지·좌표는 추측으로 채우지 않고 복구 대상에 기록한다.

## 3. 메타데이터: 검색 필드와 상세 정보를 나눠 보강

### 3.1 저장 위치

| 위치 | 담을 정보 | 이유 |
|---|---|---|
| Milvus의 명시적 scalar 필드 | 검색 조건, 문서/개정/청크 ID, 출처 종류, 품질 상태, 매핑 버전 | 필터·그룹화·결과 연결에 필요한 작은 필드 |
| 문서/청크 메타 저장소 | 제목·문서번호·개정 정본, 최신 권한, 출처 위치, 부모/이웃 연결, 처리 이력 | 상세 정보와 변경이 잦은 문서 단위 속성 관리 |
| 파일/객체 저장소 | 원문, 청크 본문 산출물, 이미지, OCR 상세 결과·좌표 | 큰 데이터를 모든 검색 결과와 메모리에 중복시키는 비용 억제 |

기존 본문이 Milvus에 저장되어 있으면 이동 비용과 추가 조회 지연을 함께 비교한다. 외부 본문 저장소의 배치 조회 계약이 준비되기 전에는 본문 필드를 제거하지 않는다. 검색 응답에서는 우선 ID·점수·필수 메타만 받고, 선정된 후보의 본문을 묶어서 조회하는 방법을 평가한다. 반환 필드 축소와 컬렉션의 실제 RAM 절감은 따로 측정한다.

### 3.2 필드 설계안

아래는 논리 계약이다. 현재 필드명·PK와 매핑한 뒤 길이·타입을 확정한다. 기존 PK가 안정적이면 그대로 보존한다. 새 `chunk_id`를 만들 경우 원본 PK와의 일대일 매핑을 보관하고 AutoID에 의한 ID 변경을 방지한다.

| 묶음 | 필드 예시 | 용도·보강 기준 |
|---|---|---|
| 식별 | `chunk_id`, `source_document_id`, `revision_id` | 필수. 문서·개정·청크를 유일하게 연결; 제목으로 조인하지 않음 |
| 검색 범위 | `site_id`, `document_type`, `language`, `lifecycle_state` | 실제 검색에 쓰는 속성만 Milvus에 복제; NULL/미확인을 유효·공개로 간주하지 않음 |
| 권한 | `acl_scope_ids`, `acl_version` 또는 정본 권한 계약에 맞는 필드 | 단일 Site/부서를 전체 권한 규칙으로 대체하지 않음; 다중 권한이면 ARRAY 등 지원 타입·연산 검증 |
| 근거 품질 | `origin_type`, `quality_status` | 본문/OCR/표와 검증·미확인·격리 상태 구분; 서비스 필터에 사용 |
| 위치·연결 | `source_locator_ref`, `parent_chunk_id`, `chunk_ordinal` | 상세 저장소의 페이지/슬라이드/시트·절/셀·bbox, 앞뒤 청크로 연결 |
| 재현성 | `content_hash`, `embedding_input_hash`, `embedding_profile_id`, `metadata_version` | 청크 텍스트, 실제 임베딩 입력, 모델·차원·정규화·prefix 설정, 메타 변환 버전 추적 |
| 상세 표시 | 제목, 문서번호, 개정일/발효일, 담당 조직, 업무 분류 | 문서/개정 메타에 저장; 정확 일치 필터용 문서번호 등 필요한 항목만 scalar로 복제 |
| 확장 | 태그, 설비/제품/프로젝트, 요약, 관련 문서 | 정본 매핑 우선. 추론한 값은 생성 방법·버전·검증 상태를 구분하여 저장 |

`source_locator_ref`의 상세 정보에는 위치 단위와 기준을 함께 둔다. 예를 들어 PDF 물리 페이지와 인쇄 페이지 번호, bbox의 좌표계·단위는 구분한다. 같은 이미지가 여러 문서에 등장하면 OCR 결과를 재사용하되 각 문서·개정의 위치와 권한 연결은 유지한다.

형태가 자주 바뀌는 상세 속성은 JSON으로 관리할 수 있다. 그러나 자주 필터링하는 핵심 키는 타입을 고정한다. JSON 안의 모든 키가 자동으로 인덱싱된다고 가정하지 않는다. `VARCHAR.max_length`는 UTF-8 바이트 길이를 기준으로 설치 버전의 제약과 실제 최댓값을 확인한다. [VarChar 필드](https://milvus.io/docs/string.md).

### 3.3 보강 순서와 재임베딩 경계

1. **P0 — 정본과 출처:** ID·개정·원문 위치·권한·폐기 상태·본문/OCR·품질 상태를 기존 파일/파싱 산출물과 G-HeSS 메타에서 연결한다.
2. **P1 — 검색 품질:** 절 제목·부모 청크·표 제목/헤더·문서번호 정규화·중복 그룹·업무 분류를 보강한다. 저장한 태그만으로 벡터 의미 검색이 개선되는 것은 아니며 필터·키워드 검색·재랭킹에 실제 사용한다.
3. **P2 — 선택적 생성:** 요약·예상 질문·추출 엔티티는 검색 실패 유형과 수요를 보고 추가한다. 전량 LLM 호출을 이관의 선행 조건으로 두지 않는다.

| 변경 | 기존 벡터 재사용 | 남는 작업 |
|---|---|---|
| 페이지·출처·권한·분류·제목을 별도 메타로 추가 | 가능 | 메타 갱신·필터/출처 연결 평가 |
| 인덱스·샤드·컬렉션 서버 변경 | 가능 | 복사·색인·load·검색 검증 |
| 제목/절 경로를 **임베딩 입력에** 새로 붙임 | 변경된 청크는 재계산 | 새 입력 hash·프로필로 선택적 임베딩 |
| OCR 정정·청크 분할/본문 변경 | 변경 청크는 재계산 | 출처·부모 연결과 영향 범위 재검증 |
| 임베딩 모델·차원·전처리/정규화 규칙 변경 | 동일 벡터 공간 보장 없으면 재사용 불가 | 별도 세대에서 대상 재임베딩·회귀 평가 |

## 4. 프로덕션 이관 경로와 절차

### 4.1 경로 선택

| 경로 | 적합한 조건 | 주의할 점 |
|---|---|---|
| A. 원본 서버에서 새 컬렉션 완성 → Milvus Backup/Restore | 메타데이터·파티션 구조 변경을 원본 서버에서 먼저 끝내고 검증된 컬렉션을 그대로 옮김 | 서버·도구 호환성, 백업 저장소 접근, 장시간 작업 중 부하, 복원 후 인덱스 재구축 여부 확인 |
| B. Parquet 생성 → 프로덕션 Bulk Import | 야간 창마다 독립 배치로 천천히 적재하거나 이관 과정에서 필드 변환이 필요함 | 파일 분할·객체 저장소·manifest·중복 방지·import 동시성 관리 필요 |
| C. Database 전체 Backup/Restore | 해당 DB의 모든 컬렉션을 함께 동일 시점으로 옮겨야 함 | 불필요한 컬렉션과 데이터까지 포함될 수 있어 저장소·복원 시간·충돌 범위 증가 |
| D. 동일 로직으로 전체 재임베딩 → 새 컬렉션 적재 | 기존 벡터의 생성 계약·무결성을 신뢰하기 어렵거나 export보다 원문 청크 재생성이 안전함 | 계산 자원·약 30.34억 입력 토큰 가정·며칠의 처리시간, 버전 차이에 따른 벡터 drift |

**현재 요구에는 A를 기본안으로 제안하고 D를 pilot 비교안으로 둔다.** 원본 서버의 별도 컬렉션에서 메타데이터 구조와 파티션을 먼저 완성하고 대사한 뒤, 그 컬렉션만 프로덕션 서버로 옮기면 대상 서버에서 758만 행을 다시 변환하는 작업을 피할 수 있다. 원본 운영 컬렉션은 직접 변경하지 않고 `ghess_chunks_v2_20260918` 같은 별도 이름을 사용한다. 동일한 청크 텍스트와 정확히 같은 BGE-M3 처리 계약이라면 재임베딩 자체가 검색 품질을 높이지는 않으므로, D는 무결성·재현성·운영 단순화에서 이득이 확인될 때 선택한다.

Milvus Backup은 메타데이터와 세그먼트 데이터를 읽어 대상에 새 컬렉션을 복원한다. Database 단위와 컬렉션 단위를 모두 지원하며 현재 CLI의 filter 문법은 아래처럼 구분한다. 실제 실행 전 설치한 `milvus-backup` 버전의 도움말과 호환표로 옵션을 다시 확인한다.

```text
Database 단위:   --filter 'database_name.*'
컬렉션 단위:     --filter 'database_name.collection_name'
인덱스 재구축:   restore 시 --rebuild_index 사용 여부를 사전 리허설로 결정
```

restore에서 suffix 또는 rename을 함께 쓰면 `--filter`에는 **변경 후 대상 이름**을 넣는다. 변경 전 이름을 쓰면 아무 컬렉션도 복원하지 않고 명령은 성공으로 끝날 수 있으므로, 실행 로그의 실제 대상 컬렉션 목록과 복원 후 row count를 반드시 확인한다.

Milvus Backup은 스키마 변환 도구가 아니다. 새 메타데이터 구조는 백업 전에 원본 서버의 새 컬렉션에 반영해야 한다. Milvus 외부의 청크 본문·문서 메타·권한 매핑·애플리케이션 설정도 별도로 보존한다. 원본·대상 Milvus와 `milvus-backup`의 정확한 버전을 고정하고 [호환표와 사용법](https://github.com/zilliztech/milvus-backup/blob/main/README.md)을 확인한다. [Milvus Backup 개요](https://milvus.io/docs/v2.6.x/milvus_backup_overview.md).

Parquet은 이관 파일 형식이고 Bulk Import는 대상 Milvus가 해당 파일을 읽어 적재하는 기능이다. Milvus BulkWriter 등으로 schema에 맞는 Parquet 파일을 만들고 프로덕션 Milvus가 접근할 수 있는 MinIO/S3 계열 객체 저장소에 올린 뒤 import job을 제출한다. Parquet 파일 자체가 컬렉션·인덱스·alias·복구 절차를 관리하지 않으므로 manifest와 작업 상태 관리는 별도로 구현한다. [Bulk Import](https://milvus.io/docs/v2.6.x/import-data.md), [입력 파일 준비](https://milvus.io/docs/v2.6.x/prepare-source-data.md).

여러 날의 야간 창마다 작업을 명확히 끊어야 한다면 B가 더 다루기 쉽다. Milvus Backup/Restore를 선택하면 중간에 강제로 종료하지 말고, 사용자가 없는 시간에 시작하여 낮에도 낮은 동시성으로 계속 실행하거나 비서비스 대상 서버에서 완료하도록 인프라팀과 합의한다.

기존 컬렉션의 필드 추가를 선택할 경우, 공식 문서는 scalar 필드 추가를 2.6.x 이상에서 지원하고 추가 필드의 `nullable=True`를 요구한다. 미보강 기존 행은 NULL 또는 지정 기본값이므로 누락 상태부터 검사한다. 부분 upsert는 2.6.2 이상에서 `partial_update=True`를 지원한다. 구버전의 일반 upsert를 메타만 바꾸는 API로 사용하지 않는다. 지원이 없으면 기존 벡터를 포함한 전체 행을 보존해 갱신하거나 B를 사용한다. 부분 갱신도 전량 수행할 때의 쓰기·세그먼트 정리 비용은 측정한다. [스키마 변경](https://milvus.io/docs/add-fields-to-an-existing-collection.md), [Upsert](https://milvus.io/docs/upsert-entities.md).

### 4.2 실행 순서

1. **원본을 보존하고 기준점을 잡는다.** 현재 운영 컬렉션의 복원 가능한 안전 백업을 먼저 만들고 수집/적재 작업의 기준점 `W0`와 대상 manifest를 기록한다. 계속 변경을 받아야 하면 삽입·개정·삭제·권한 변경을 모두 재생할 수 있는 변경 로그나 이중 쓰기를 준비한다.
2. **원본 서버에 새 컬렉션을 만든다.** 예: `ghess_chunks_v2_20260918`. 모델·차원·dtype·COSINE을 기존 벡터와 맞추고, 확정한 scalar 필드·샤드·파티션 구조를 컬렉션 생성 시 적용한다. 기존 운영 컬렉션은 직접 변형하지 않는다.
3. **기존 벡터와 보강 메타를 결합한다.** 보존된 임베딩 산출물이 있으면 우선 사용하고, 없으면 지원되는 query iterator로 원본 PK·벡터·필드를 읽는다. 큰 offset 페이지 순회는 피한다. 문서/개정/권한/출처 연결을 새 schema에 맞춰 적재한다. 재임베딩안을 선택하면 같은 PK와 청크 텍스트로 새 벡터를 만들고 생성 계약과 배치 상태를 manifest에 기록한다.
4. **원본 서버의 새 컬렉션을 대사한다.** 정확한 행 수 7,585,436개, PK 집합, 문서·사이트·카테고리·개정·출처별 분포, 벡터 표본 해시, 필수 메타 누락을 검사한다. 사이트 제한 검색과 전체 검색을 모두 실행한다.
5. **소규모 이관 리허설을 수행한다.** 약 5%인 **약 379,272개 청크** 또는 30만~50만 청크로 백업/복원, Parquet Bulk Import, 동일 로직 재임베딩 후보를 끝까지 수행하여 처리량·메모리/GPU·네트워크·재시도 방식과 검색 결과를 비교한다. 이 실측값으로 경로·전체 일정·동시성을 확정한다.
6. **검증된 컬렉션을 프로덕션으로 옮긴다.** 기본안은 컬렉션 단위 Milvus Backup/Restore다. 야간마다 독립 배치가 필요하면 512MiB 안팎의 Parquet 파일에서 시작해 Bulk Import한다. 대상 컬렉션은 적재 중 unload 상태를 유지한다.
7. **전체 적재가 끝난 뒤 인덱스를 만든다.** import/restore 완료와 행 대사를 먼저 끝내고 HNSW를 별도 작업 창에서 구축한다. 인덱스 진행률 100%와 load 성공을 확인한 뒤 대표 질의와 부하 시험을 수행한다.
8. **증분을 따라잡고 연결을 전환한다.** 최종 쓰기 경계 `W1`을 잠깐 잡아 `W0~W1` 변경을 재생·검증하고 새 쓰기 작업을 대상 서버로 전환한다. 서로 다른 서버 사이의 전환에는 애플리케이션 endpoint·database·collection 설정 변경이 필요하다.
9. **복귀 가능 상태로 관찰한다.** 초기 일부 트래픽 → 확대 → 전체 전환마다 오류·p95·근거 품질·최신성을 확인한다. 최소 한 업무일을 포함한 관찰 기간 동안 이전 컬렉션·백업·변경 로그를 유지한다.

배치 기록에는 `migration_id, source_generation, batch_id, file_name, file_hash, expected_rows, PK 목록/범위, import_job_id, status, imported_rows, completed_at`을 남긴다. 완료 배치는 재실행에서 건너뛴다. **고정 PK라도 insert/import가 자동으로 중복 제거해 준다고 가정하지 않는다.** timeout으로 성공 여부를 모르면 작업 상태와 PK를 확인한 후 재개하고, 필요하면 검증한 upsert 경로나 미노출 대상의 해당 배치를 재구성한다. 동일 문서/PK의 갱신은 순서를 보장하고 오래된 작업이 새 메타를 덮지 못하게 한다.

### 4.3 야간 분할 이관 운영

사용자가 없는 야간 시간에 며칠에 걸쳐 이관하는 방식은 안전한 선택이다. 한 번 제출한 큰 작업을 매일 아침 강제 종료하는 방식은 피하고, 각 야간 창 안에 끝날 수 있는 독립 배치로 나눈다.

| 시점 | 작업 | 운영 원칙 |
|---|---|---|
| 사전 준비 | 원본 안전 백업, manifest, 새 schema와 빈 대상 컬렉션 검증 | 서비스 영향 없는 읽기·복구 시험까지 완료 |
| 1일차 야간 | 30만~50만 청크 이관 및 재임베딩 pilot | 각 경로의 처리량·peak RAM/GPU·CPU·I/O·네트워크·실패 복구 측정 |
| 2일차~N일차 야간 | pilot 결과에 맞춘 독립 배치 import/restore | 다음날 업무 시작 1~2시간 전 신규 job 제출 중단 |
| 전체 적재 후 야간 | 행 대사, HNSW 생성, load | import와 HNSW 빌드를 동시에 수행하지 않음 |
| 최종 전환 야간 | `W1` 증분 반영, 검색 검증, endpoint 전환 | 복귀 시험 후 제한 트래픽부터 확대 |

진행 중인 import job은 가능하면 완료시킨다. 낮 동안 서비스 영향이 우려되면 새 job만 제출하지 않고 대상 컬렉션은 unload 상태로 둔다. 배치 크기는 pilot의 시간당 처리량과 야간 가용 시간으로 정한다. 이 방식은 Parquet Bulk Import에 특히 적합하다. Milvus Backup/Restore는 작은 컬렉션 단위가 아닌 한 작업을 임의로 끊어 재개하는 용도로 사용하지 않는다.

### 4.4 OOM 및 자원 통제

OOM 가능성은 있다. 758만 벡터를 한 번에 읽는 애플리케이션, 높은 import 동시성, HNSW 구축, 구·신 컬렉션 동시 load가 주요 위험이다.

| 단계 | OOM 위험 | 통제안 |
|---|---|---|
| export/Parquet 생성 | 중간 | iterator/streaming 사용, 벡터 전량 메모리 적재 금지, 파일 단위 해제 |
| 동일 로직 재임베딩 | 중간~높음 | 청크·벡터 streaming, GPU/embedding API 동시성 제한, 배치별 결과 즉시 적재·해제 |
| Bulk Import/restore | 중간 | Parquet 약 512MiB에서 시작, import 동시성 2로 pilot 후 3~4까지 단계 확대 |
| HNSW 빌드 | 높음 | 전체 import 완료 후 별도 작업 창에서 생성, 빌드 전후 peak RSS와 임시 디스크 측정 |
| collection load | 높음 | 새 컬렉션만 먼저 load 시험, replica 1에서 시작, load 진행 중 다른 대형 작업 금지 |
| 구·신 컬렉션 동시 load | 매우 높음 | 메모리가 빠듯하면 구 컬렉션 release 후 신 컬렉션 load; 두 세대 합산 메모리 사전 산정 |

Milvus 2.6 문서의 `dataNode.import.maxConcurrentTaskNum` 기본값은 16, `dataNode.import.readBufferSizeInMB` 기본값은 16MiB다. 기본 동시성이 작은 장비에는 공격적일 수 있으므로 실제 배포값과 DataNode 수를 인프라팀에 확인하고, 애플리케이션에서 동시에 제출하는 job 수는 2부터 시작한다. [DataNode 설정](https://milvus.io/docs/v2.6.x/configure_datanode.md).

메모리가 부족할 때의 실행 순서는 다음과 같다.

1. 대상 컬렉션을 unload 상태로 import한다.
2. 전체 행 대사 후 다른 대형 작업을 중지한다.
3. HNSW를 생성하고 peak RAM·임시 디스크를 확인한다.
4. replica 1로 load한다.
5. 구 컬렉션과 동시에 load할 여유가 없으면 전환 창에서 구 컬렉션을 release한 뒤 새 컬렉션을 load한다.
6. NVMe가 있고 RAM 병목이 계속되면 mmap 또는 압축/디스크 인덱스를 별도 성능 시험한다. mmap은 cold latency와 IOPS를 함께 본다. [mmap](https://milvus.io/docs/v2.6.x/mmap.md).

### 4.5 예상 처리 시간

아래 시간은 **16~32 vCPU, RAM 128GiB 이상, NVMe, 1Gbps 이상 네트워크를 가정한 계획 범위**다. Milvus 버전·서버 사양·메타 크기·세그먼트 수·인덱스 종류가 확인되지 않았으므로 pilot 전 확정 일정으로 사용하지 않는다. RAM 128GiB는 시작점이며 공식 최소 사양을 뜻하지 않는다.

#### 기존 벡터 이관

| 작업 | 계획 범위 | 큰 변동 요인 |
|---|---:|---|
| 안전 백업 또는 Parquet 생성 | 1~5시간 | 원본 세그먼트 수, 객체 저장소 I/O, 메타 결합 비용 |
| 서버 간 전송 | 10분~2시간 | 실제 백업 크기, 네트워크 대역폭, 암호화/압축 |
| restore 또는 Bulk Import | 2~8시간 | CPU·스토리지 처리량, 파일 크기와 수, 동시성 |
| HNSW 구축 | 2~10시간 | `M`, `efConstruction`, CPU, RAM, 세그먼트 구성 |
| collection load | 10분~1시간 | 인덱스/원시 데이터 크기, 디스크·페이지 캐시 |
| 대사·검색 검증 | 1~2시간 | 샘플 수, PK/해시 대사 방식, 부하 시험 범위 |
| **총 계획 범위** | **약 6~26시간** | 병렬 실행을 전제로 줄이지 않고 단계별 합산 |

청크 처리량만으로 본 7,585,436개 전체 이관 시간은 다음과 같다. 이 값에는 백업 준비·인덱스 생성·검증 시간이 포함되지 않는다.

| 실측 처리량 | 청크 적재 시간 |
|---:|---:|
| 25만 개/시간 | 약 30.3시간 |
| 50만 개/시간 | 약 15.2시간 |
| 100만 개/시간 | 약 7.6시간 |
| 200만 개/시간 | 약 3.8시간 |
| 400만 개/시간 | 약 1.9시간 |

실무 일정은 **2개 야간 + 1개 예비 야간**을 우선 확보한다. 첫날 pilot이 50만 개/시간보다 느리거나 HNSW가 10시간을 넘으면 3~5개 야간으로 늘린다. 장시간 작업이 서비스에 영향 없이 계속될 수 있는 별도 프로덕션 서버라면 restore/import 자체는 낮에도 저동시성으로 진행하고, HNSW·load·전환만 야간에 수행할 수 있다.

#### 동일 로직 전체 재임베딩

재임베딩 전에 “동일 로직”을 다음 값으로 고정한다: BGE-M3 모델 artifact/revision과 checksum, tokenizer revision, 청크 텍스트 hash, 최대 입력 길이와 truncation, pooling, query/document prefix, dense 출력 선택, 정규화 여부, 추론 dtype(FP32/FP16/BF16), 라이브러리·컨테이너 버전. 하나라도 다르면 같은 모델명이어도 기존 벡터와 같은 생성으로 간주하지 않는다.

현재 용량 계산의 가정은 평균 400토큰/청크, 임베딩 최대 40청크/초, 2,000,000 TPM, 실효율 70%다.

```text
총 입력 토큰 = 7,585,436 × 400 = 3,034,174,400토큰
실효 청크/초 = min(40, 2,000,000 / (60 × 400)) × 0.70 = 28청크/초
재임베딩 시간 = 7,585,436 / 28 / 3,600 = 약 75.3시간
```

이 가정에서는 TPM보다 40청크/초 처리 한도가 병목이다. 5% pilot인 약 379,272개 청크는 약 **3.8시간**이다. pilot의 실제 완료 행 수를 GPU/API 가동 시간으로 나눈 지속 처리량으로 전체 시간을 다시 산정한다.

| 지속 실효 처리량 | 전체 재임베딩 시간 | 14시간 야간 창의 이론상 횟수 |
|---:|---:|---:|
| 5청크/초 | 약 421.4시간 | 약 30.1회 |
| 10청크/초 | 약 210.7시간 | 약 15.1회 |
| 20청크/초 | 약 105.4시간 | 약 7.5회 |
| **28청크/초(현재 계획값)** | **약 75.3시간** | **약 5.4회** |
| 40청크/초 | 약 52.7시간 | 약 3.8회 |
| 80청크/초 | 약 26.3시간 | 약 1.9회 |
| 160청크/초 | 약 13.2시간 | 약 0.9회 |

현재 계획값이면 재임베딩에 최소 6개 야간, HNSW·검증·전환에 1개 야간, 장애 대비 1개 예비 야간을 잡아 **약 7~8개 야간**으로 계획한다. 24시간 연속 처리할 수 있으면 재임베딩 약 3.1일에 HNSW·검증 3~12시간을 더해 **약 3.3~3.7일**이 계획 범위다. Milvus 적재가 임베딩보다 느리거나 실패 재처리가 있으면 더 길어진다.

재임베딩을 선택할 조건은 다음과 같다.

- 기존 벡터의 모델 revision·전처리·정규화·입력 hash를 확인할 수 없거나 여러 생성 방식이 섞여 있다.
- 원본 벡터 export의 안정성·시간이 재임베딩보다 나쁘다는 pilot 결과가 있다.
- 벡터 손상·차원 불일치·비유한값·PK 매핑 오류가 발견되고 원본 청크 텍스트는 신뢰할 수 있다.
- 메타데이터 변경을 넘어 청크 텍스트, 제목/절 prefix 등 **임베딩 입력**이 바뀐다.

기존 벡터 대사와 검색 품질이 통과하고 입력 텍스트도 그대로라면 A를 유지한다. D를 선택하더라도 기존 컬렉션을 기준선으로 보존하고, 같은 평가 질의의 ANN 결과·업무 Recall·p95를 새 컬렉션과 비교한 뒤 전환한다.

### 4.6 대사와 전환 조건

| 검증 | 통과 기준 |
|---|---|
| 대상 문서 | 정확한 대상 목록의 모든 문서가 완료 또는 사유 있는 격리로 대사됨; 약 61,000이라는 반올림 숫자와 비교해 끝내지 않음 |
| 행·키 | 원본 PK 집합 = 대상을 원본 PK로 역매핑한 집합 ∪ 명시적 제외 집합; 두 집합은 겹치지 않으며 예상 밖 PK·매핑 충돌·원인 불명 누락 0 |
| 분포 | 문서/개정·본문/OCR·상태별 청크 수 일치; 총합만 맞고 일부 문서가 빠진 경우 차단 |
| 벡터 | 재사용 경로는 차원·dtype·유한값과 결정적 직렬화 해시 대조. 재임베딩 경로는 생성 계약 일치, 표본의 기존/신규 cosine 분포와 허용 오차, ANN·업무 검색 회귀를 기록 |
| 메타·출처 | 필수 필드와 참조 무결성 검사; 대표 원문에서 페이지/절·개정·본문 확인; NULL 권한/출처를 정상값으로 채우지 않음 |
| 검색 | 동일 필터·모델·거리 척도에서 ANN recall과 사람 판정 근거 품질 통과; 인덱스 재구성에 따른 순위 차이는 평가로 판별 |
| 운영 | index/load 상태, 리소스 여유, `W1` 반영, 읽기·쓰기 연결 전환, 복귀 리허설 기록 |

대용량 해시는 배치별 PK 정렬과 원래 벡터 dtype의 바이트 규칙을 고정해 계산한다. JSON의 소수점 출력 문자열이나 행 반환 순서를 그대로 비교하지 않는다. 불일치가 있으면 배치와 PK로 범위를 좁힌다.

### 4.7 Alias와 복귀 경계

동일 Milvus DB 안에서 컬렉션 세대를 바꿀 때는 `ghess_chunks_active` 같은 별도 alias를 사용할 수 있다. alias는 준비된 컬렉션으로 다시 연결할 수 있다. **서로 다른 서버로의 최초 이관은 alias 하나만 바꾸어 완료되지 않는다.** 애플리케이션 연결 정보도 함께 바꾼다. [Alias 관리](https://milvus.io/docs/manage-aliases.md).

요청 시작 시 `endpoint/database/physical_collection/generation`을 고정하여 한 질문의 첫 검색과 보완 검색이 서로 다른 세대를 읽지 않게 한다. 검색 캐시 키에도 generation을 포함한다. 메타 저장소·G-HeSS·애플리케이션 설정과 alias 갱신을 하나의 원자적 트랜잭션으로 보지 않는다.

오류·품질 회귀로 복귀할 때는 이전 연결 묶음을 복원한다. 이미 새 문서·개정·삭제·권한 변경을 받았다면 변경 로그를 구 세대에 반영하거나 최신성 검사를 통해 사용 불가 문서를 차단한다. **최신 데이터가 없는 구 컬렉션으로 되돌아가는 것만으로 정상 복귀가 되지는 않는다.** 로그 재생이 불가능하면 최신 답변을 제한하는 축소 운영을 선택한다.

## 5. 샤드·파티션·인덱스·복제 설정 후보

### 5.1 샤드와 파티션

샤드는 데이터 입력 채널과 연결된다. 샤드를 늘리면 입력 분배가 달라지고 검색의 분산 요청·병합 비용도 달라질 수 있다. sealed 세그먼트는 QueryNode에 분산될 수 있으므로 샤드 수를 읽기 서버 수와 같게 맞출 필요는 없다. [컬렉션 생성](https://milvus.io/docs/create-collection.md), [데이터 처리](https://milvus.io/docs/data_processing.md).

| 조건 | 초기 실험안 |
|---|---|
| 단일 서버, 읽기 중심, 쓰기 병목 미확인 | 샤드 1개를 기준선으로 측정 |
| 여러 쓰기 처리 노드, 적재 병목/분배 불균형 확인 | 같은 데이터로 1개와 2개 비교; 필요한 경우에만 4개 확장 |
| 검색 QPS 또는 장애 대응이 문제 | ANN/필터·QueryNode 자원·질의 복제본을 별도로 검토 |
| Site 필터가 대부분의 질의에 존재 | scalar 필터부터 측정하고 partition key 추가 효과 비교 |

초기안은 **샤드 1개**다. 758만 건의 일괄 적재에서 쓰기 병목이 확인되면 동일 pilot로 2개를 비교하고, 4개는 2개에서도 병목이 확인될 때만 검토한다. 샤드 수는 새 컬렉션을 만들 때 결정한다. **원본 파일 95GB를 Milvus 삽입 데이터 95GB로 환산하지 않는다.**

새 컬렉션을 만들 때 파티션 구조를 정하고 각 행을 해당 파티션으로 적재하면 이관과 동시에 적용할 수 있다. 파티션을 생성하는 것만으로 기존 행이 사이트나 카테고리에 따라 자동 분류되지는 않는다.

| 방식 | 동작 | 적합한 경우 | 주의할 점 |
|---|---|---|---|
| 수동 파티션 | 애플리케이션이 지정한 물리 파티션에 행을 적재 | 사이트 수가 적고 안정적이며 대부분의 검색이 특정 사이트를 명시 | 신규 사이트 운영, 잘못된 라우팅, 전체 조회 fan-out 관리 필요 |
| Partition Key | 지정한 scalar 키 값을 Milvus가 해시하여 여러 파티션에 분산 | 키 조건이 대부분의 검색에 있고 값 종류가 많음 | 사이트당 물리 파티션 하나가 아니며 검색 필터에 partition key 조건이 있어야 pruning 가능 |
| scalar 필드만 사용 | 전체 컬렉션에서 `site_id`·`category_id` 필터 | 전체 검색이 잦거나 사이트/카테고리가 자주 바뀜 | 필터가 많은 경우 scalar 인덱스와 실제 지연 측정 필요 |

**사이트별 파티션은 사이트 제한 검색에는 유리할 수 있지만 전체 조회에서는 이점이 줄고 여러 파티션의 결과를 모으는 비용이 생길 수 있다.** 전체 조회 비율이 높다면 `site_id` scalar 필드와 인덱스를 먼저 적용한다. 사이트 수가 제한적이고 안정적이며 사이트 제한 검색이 대부분이라는 로그가 확인될 때 수동 파티션과 전체 검색 p95를 비교한다.

문서 카테고리는 중복·변경 가능성이 있고 여러 카테고리를 가질 수 있으므로 기본안은 `category_id` scalar 필드다. 최상위 카테고리 하나가 안정적으로 정해지고 카테고리 제한 검색이 압도적으로 많을 때만 파티션 후보로 올린다. 너무 많은 파티션과 작은 세그먼트는 검색 fan-out과 관리 비용을 늘릴 수 있다. 사용자/문서마다 파티션을 만들거나 권한 제어를 파티션만으로 해결하지 않는다. [파티션 관리](https://milvus.io/docs/v2.6.x/manage-partitions.md), [Partition Key](https://milvus.io/docs/v2.6.x/use-partition-key.md).

### 5.2 Dense 벡터와 scalar 인덱스

현재 BGE-M3 + COSINE 검색을 첫 기준선으로 남긴다. 다음 HNSW 후보는 dense 벡터 필드의 실제 타입과 충분한 RAM이 확인됐을 때 적용한다. BGE-M3라는 모델명만으로 HNSW 최적값이 정해지지는 않는다.

| 항목 | 실험 시작값 | 판단 |
|---|---|---|
| 벡터 인덱스 | 현재 인덱스 vs `HNSW` | ANN recall·p95·RAM·빌드 시간 비교 |
| Dense 차원 | BGE-M3 표준 출력 `dim=1024` | 실제 schema·표본 벡터 길이와 일치 확인 |
| 거리 척도 | 사용자 확인된 `COSINE` 유지 | 인덱스와 검색 요청에서 같은 척도 사용 |
| HNSW 빌드 | `M=16`, `efConstruction=200` | recall 미달이면 `M=32` 또는 construction 후보를 추가해 재빌드 |
| HNSW 검색 | `ef=64 / 128 / 256`, `topK=40` | `ef`는 요청 topK 이상으로 두고 선택; 검색 조정은 재임베딩 없이 가능 |
| 문서/개정/문서번호 등 정확 조건 | `INVERTED` 후보 | 실제 등호·IN·범위 조건의 비용 비교 |
| 종류가 적은 상태/출처 필드 | `BITMAP` 후보 | 값의 종류 수와 실제 필터 비율이 작고 적합한 타입일 때 |
| 권한 배열·확장 JSON | 대상 버전과 연산에 맞는 인덱스 | 일반 문자열 필드와 같은 지원 범위라고 가정하지 않음 |

HNSW 항목의 의미와 조정 방향은 다음과 같다.

- **`M`:** 각 벡터 노드가 그래프에서 유지하는 연결 수다. 값을 높이면 연결이 촘촘해져 recall이 좋아질 수 있지만 인덱스 RAM·빌드 시간·검색 계산량이 늘어난다. 변경하려면 인덱스를 다시 만들어야 한다.
- **`efConstruction`:** 인덱스를 만들 때 각 벡터의 이웃 후보를 얼마나 넓게 탐색할지 정한다. 높을수록 그래프 품질과 recall이 좋아질 가능성이 있지만 빌드 시간과 peak 자원이 증가한다. 변경하려면 인덱스를 다시 만들어야 한다.
- **검색 `ef`:** 질의마다 탐색하는 후보 목록 크기다. 높이면 recall과 지연이 함께 증가한다. 인덱스를 다시 만들지 않고 요청별로 조정할 수 있으며 `topK` 이상으로 둔다.
- **`topK`:** 검색 결과로 최종 반환할 후보 개수다. HNSW 구조 파라미터가 아니라 서비스 요구값이며, 재랭킹과 문서 중복 제거에 필요한 후보 수를 기준으로 정한다.
- **`COSINE`:** 벡터 방향의 유사도를 비교하는 거리 척도다. 현재 데이터와 질의 모두 같은 BGE-M3 처리 계약을 사용하고 인덱스 생성과 검색 요청에 동일하게 지정한다.

위 숫자는 공식 기본값이나 최적값이 아니다. BITMAP은 값의 종류가 적은 scalar 필드가 주 대상이다. 모든 메타 필드에 인덱스를 만들지 않고 자주 쓰는 조건부터 측정한다. [HNSW](https://milvus.io/docs/v2.6.x/hnsw.md), [BITMAP](https://milvus.io/docs/v2.6.x/bitmap.md), [Scalar index](https://milvus.io/docs/v2.6.x/index-scalar-fields.md).

기본 필터는 권한·상태·개정 계약을 만족하도록 서비스에서 만든다. 복잡한 필터가 지연을 지배하면 Milvus가 지원하는 standard/iterative filtering을 비교한다. 필터를 통과하는 데이터가 적은 경우의 지연·결과 수 부족도 측정한다. [Filtered search](https://milvus.io/docs/filtered-search.md).

#### BGE-M3에 따른 추가 확인

- **질의·문서 임베딩 계약:** 같은 모델 리비전·전처리·pooling·입력 길이 제한을 기록하고 검색 질의도 대응되는 설정을 사용한다. 공식 BGE-M3는 질의 instruction을 필수로 요구하지 않으므로 기존 파이프라인의 prefix 사용 여부를 확인한 뒤 변경을 평가한다. 최대 입력 8,192토큰은 모델의 지원 길이이며 현재 청크 길이·절단 설정의 확인값은 아니다. [BGE-M3 사용법](https://huggingface.co/BAAI/bge-m3).
- **COSINE 유지:** 단위 길이로 정규화한 벡터끼리는 IP와 COSINE이 같은 유사도를 계산하지만, 현재 이관의 기준선은 COSINE으로 유지한다. 사용자 확인만으로 벡터가 사전에 정규화됐다고 판단하지 않는다. [Milvus 유사도 척도](https://milvus.io/docs/metric.md).
- **저장 dtype:** 추론을 FP16으로 수행했어도 Milvus 저장 필드가 `FLOAT_VECTOR`이면 차원당 4바이트 기준이다. 모델 추론 정밀도와 저장 dtype을 별도로 확인한다.
- **Dense 외 출력:** BGE-M3는 sparse 토큰 가중치와 ColBERT 방식의 multi-vector 출력도 지원한다. 현재 보존 여부는 미확인이다. sparse가 저장돼 있으면 dense와의 병합을 실험할 수 있고, 없으면 보존한 청크 텍스트로 sparse를 추가 생성해야 한다. 기존 dense 벡터만으로 이 출력을 복원할 수 있다고 가정하지 않는다. sparse는 별도 필드·인덱스로 설계하고 기존 G-HeSS 키워드 검색과 비교한다. [BGE-M3 출력 방식](https://huggingface.co/BAAI/bge-m3).

### 5.3 복제본과 메모리

성능 비교는 복제본 1개에서 출발할 수 있다. 실제 운영에서 Distributed 구성과 장애 시에도 충분한 자원이 확보되면 질의 복제본 2개를 검토한다. 각 복제본 그룹은 전체 검색 데이터의 복사본을 적재하며 여러 QueryNode로 구성될 수 있다. 복제본 2개는 검색 처리량·가용성에 도움을 줄 수 있지만 단일 검색 지연을 절반으로 보장하지 않는다. [In-memory replica](https://milvus.io/docs/replica.md).

```text
원시 벡터 바이트 = 실제 loaded 벡터 수 × 차원 × dtype 바이트
복제본별 RAM 예산 = (원시 벡터 × resident 계수 + scalar/인덱스 추가량) / 목표 이용률
                  + 프로세스 여유
전체 query RAM = 복제본별 예산 × 질의 복제본 수
```

resident 계수는 인덱스·원시 데이터·실측 적재 방식에 맞추며 이중 계산하지 않는다. 샤드 수를 늘려 전체 RAM을 그 수로 나누지 않는다. 구/신 세대를 같은 자원에 동시에 load하면 두 세대의 RAM과 빌드·compaction 임시공간을 확보한다. 다른 서버라면 각 서버의 사용량을 따로 산정한다. 메타 확장 후 scalar 크기도 다시 측정한다.

현재 확인된 7,585,436개와 1,024차원 float32 가정의 원시 벡터는 약 28.94GiB다. HNSW 그래프·원시 벡터·scalar·Milvus 프로세스와 작업 여유를 합치면 복제본당 **128GiB RAM을 보수적인 검증 시작점**으로 삼을 수 있다. 이는 공식 최소치가 아니며, pilot의 실제 load 및 index-build peak로 확정한다. 2개 질의 복제본이나 구·신 동시 load에는 이보다 훨씬 많은 총 RAM이 필요할 수 있다.

QueryNode 복제와 영속 저장소 백업/복제는 별개다. 운영 가용성은 배포 버전에 맞는 coordinator·메타 저장소·WAL/메시징·객체 저장소·네트워크의 장애 대응까지 포함해 확인한다.

## 6. 성능·품질 검증 계획

### 6.1 부하의 출발점

기존 [트래픽 산정](트래픽_리소스_산정.md#3-fastapi검색-api네트워크)에서 기준 피크는 62.5질문/분이며 Milvus 최대 2검색/질문이면 **약 2.08검색 QPS**다. 높은 시나리오는 200질문/분 → **약 6.67검색 QPS**다. 1,500명은 동시 검색 1,500개라는 뜻이 아니다. 실제 재시도·기존 서비스·배치 조회는 추가해야 한다.

| 축 | 시험 조건 |
|---|---|
| 질의 | 기존 200개 이상 평가셋: 문서번호, 자연어/약어, 표/OCR, 최신 개정, 무근거, 접근 불가 |
| 데이터 | 동일한 전체 대상 컬렉션, 동일 모델·벡터·필터·거리 척도 |
| 필터 | 통과율 약 100%/10%/1%와 실제 권한 조합, 통과 결과 0건·topK 미만도 포함 |
| 부하 | 2.1 → 6.7 → 10검색 QPS에서 시작; 10은 여유 확인용이고 실제 수요가 아님 |
| 캐시 | 재시작/load 직후와 대표 질의 워밍업 후를 분리; 캐시 적중·미적중 구분 |
| 변경 | 읽기 전용, 예상 증분 적재 동시, 메타 backfill/세그먼트 정리 동시 |
| 운영 | 부하 중 QueryNode 장애·복구, 컬렉션 전환·복귀, load 재시작 |

ANN 자체 시험은 미리 만든 질의 벡터를 사용해 임베딩 API 지연을 제외한다. 종단 시험은 FastAPI → 질의 임베딩/검색 API → Milvus → 메타/본문 조회까지 별도 측정한다. 목표 도착률을 일정하게 유지하고 처리 대기·timeout도 기록해, 느려질 때 요청량이 저절로 줄어드는 시험을 피한다.

각 주요 조건은 워밍업 후 최소 15분 또는 2,000검색 중 더 긴 구간을 제안한다. p95/p99에는 표본 수·오류 수를 함께 적는다. 최고 QPS 하나보다 운영 부하에서 품질·지연·여유가 유지되는지를 선택 기준으로 삼는다.

### 6.2 검색 근사 오차와 근거 품질을 따로 평가

- **ANN Recall@40:** 같은 전체 벡터 집합·필터·거리 척도의 정확 검색 결과와 비교한다. 질의는 샘플링할 수 있지만 비교 대상 벡터를 임의로 축소하지 않는다. 전체 FLAT 적재가 부담이면 오프라인 블록 단위 정확 거리 계산을 사용한다. 필터 통과 수가 40보다 작으면 실제 정답 집합 크기를 분모로 쓰고 0건은 별도 검사한다.
- **근거 Recall@10·문서 Recall@5:** 사람이 확인한 정답 문서/구간이 검색되는지 평가한다. ANN 이웃과 일치해도 임베딩 자체가 질문과 맞지 않을 수 있다.
- **응답 품질:** 출처·개정 일치, 표/수치 근거, 중복 상위 점유율, 접근 불가 데이터 노출과 무근거 처리까지 본다.

| 항목 | 초기 합격선 제안 |
|---|---|
| 데이터 대사 | 원인 불명 누락·추가·ID 충돌·벡터 변형 0 |
| ANN | Recall@40 ≥95%에서 시작해 업무 품질에 따라 상향; 질의 유형·필터별 결과 보고 |
| 업무 검색 | 기존 목표 유지: 문서번호 Recall@5 ≥99%, 자연어 근거 Recall@10 ≥90%; 기준선 대비 회귀 없음 |
| 단일 Milvus 검색 | 운영 부하에서 p95 ≤300ms를 예산 후보로 두고 p99·오류율 동시 기록 |
| 검색 결과 전체 | 기존 목표 p95 ≤3초 유지; 임베딩·G-HeSS·본문 조회 포함 |
| 메모리/혼합 부하 | 계획 이용률 70%에서 시작하되 실제 peak/load/빌드 여유로 보정; OOM·지속 적체 없음 |
| 권한·출처·복귀 | 기존 설계의 차단/회수·인용·최신성·복귀 시험 통과 |

이 표는 달성 보고가 아니다. ANN 숫자를 만족해도 업무 검색·권한·최신성 기준이 미달이면 전환하지 않는다. 초기 노출 범위를 줄일 때에도 평가된 제한 범위와 미지원 범위를 명시한다.

## 7. 추가 성능 개선의 선택 순서

| 순서 | 개선 | 확인할 이득·비용 |
|---|---|---|
| 1 | 인덱스/load 완료, 세그먼트 크기·수·growing 비율 점검 | 미색인 검색·과도한 분산 요청·빌드 경쟁이 있는지 확인 |
| 2 | scalar 필터, 반환 필드 축소, 문서/본문 배치 조회, SDK 연결 재사용 | Milvus/메타/네트워크 지연을 분리해 개선 |
| 3 | 문서별 후보 제한, OCR/본문 중복 억제, 부모/이웃 근거 보완 | 상위 결과 다양성·관련성, 입력 토큰과 답변 품질 |
| 4 | 기존 G-HeSS 키워드 후보와 벡터 후보의 문서 단위 RRF 병합 | 문서번호·약어·정확 명칭 개선; API 계약과 지연 확인 |
| 5 | 질의 임베딩 캐시·검색 캐시 | 모델/입력 설정, 권한 버전, 컬렉션 세대, 개정/정책에 맞는 무효화 |
| 6 | 상위 20~40개 후보의 선택적 재랭킹 | 업무 recall/순위 향상과 CPU/GPU·추가 p95 비교; 가용 모델 없으면 이관 후 과제 |
| 7 | 압축 ANN·디스크 검색·mmap | RAM 병목이 남을 때 recall·cold p99·IOPS·운영비 비교 |
| 8 | 청크/OCR/임베딩 입력 수정 | 실패 유형이 확인된 문서부터 재처리 |

insert 배치마다 `flush()`를 강제 호출하면 작은 sealed 세그먼트가 많이 생겨 검색에 불리할 수 있다. flush는 도구·운영 절차가 요구하는 경계에서 관리하고, 세그먼트 정리는 실제 분포·삭제 비율을 본 뒤 별도 시간대에 검증한다. 정리 작업도 CPU·I/O·임시공간을 사용하므로 상시 강제 실행으로 해결하지 않는다. [Flush 주의사항](https://milvus.io/api-reference/pymilvus/v2.4.x/ORM/Collection/flush.md), [성능 FAQ](https://milvus.io/docs/v2.4.x/performance_faq.md).

RAM이 부족하면 지원 버전의 `HNSW_SQ`/`IVF_SQ8` 같은 압축 인덱스, NVMe가 있는 환경의 DISKANN, mmap을 각각 후보로 둔다. 압축률을 전체 프로세스 RAM 절감률로 그대로 적용하지 않는다. mmap도 메모리를 초과하는 working set과 디스크 접근에 따라 지연이 나빠질 수 있다. [메모리 인덱스](https://milvus.io/docs/index.md), [디스크 인덱스](https://milvus.io/docs/disk_index.md), [mmap](https://milvus.io/docs/mmap.md).

기존 G-HeSS 검색 API의 품질·권한 계약이 충족되면 이를 우선 재사용한다. Milvus 내 BM25/희소 검색 신설은 한국어 분석·문서번호 처리·청크 텍스트 확보·버전 지원을 별도로 검증한 뒤 결정한다. 이관과 동시에 키워드 검색 체계를 중복 구축할 필요는 없다.

전체 응답이 느린 경우에는 구간별 시간을 먼저 본다. 기존 산정의 모델 평균 점유 30초가 실제 병목이라면 Milvus를 300ms에서 100ms로 줄여도 답변 생성 시간의 개선은 제한적이다. 검색 품질과 함께 생성 호출 수·입력 길이·출력 길이·모델 대기를 조정한다.

| OOM 또는 지연 임계치를 넘으면 누가 작업을 중단하는가? | 담당자, 연락 체계, 자동 중단 기준 | 야간 무인 작업 안전성 |

### 8.4 Milvus 설정·모니터링·복구

### 8.5 인프라팀에 전달할 초기 제안값

- 대상 컬렉션: `ghess_chunks_v2_20260918` 같은 별도 이름, BGE-M3 dense 1,024차원, COSINE.
- 데이터 규모: 문서 약 61,000개, 청크/벡터 **7,585,436개**, float32 가정 원시 벡터 약 **28.94GiB**.
- 초기 샤드: 1개, pilot에서 쓰기 병목이 확인되면 2개 비교.
- 파티션: `site_id`와 `category_id` scalar 필드 우선. 사이트 제한 검색 비율과 사이트 수를 확인한 뒤 수동 파티션 또는 Partition Key 실험.
- HNSW 시작값: `M=16`, `efConstruction=200`; 검색 `ef=64/128/256`, `topK=40` 비교.
- Bulk Import 선택 시: Parquet 약 512MiB, 동시 job 2로 시작, 대상 unload 유지.
- 동일 로직 재임베딩 대안: 평균 400토큰, 원시 40청크/초, 효율 70% 가정에서 약 75.3시간; 5% pilot으로 실제 처리량 확인.
- 작업 순서: import/restore → 행 대사 → HNSW → load → 검색 검증. 큰 작업을 겹치지 않음.
- RAM: replica 1개 검증에 128GiB 이상을 보수적 시작점으로 요청하되 pilot 실측으로 조정.
