# GHeSS 트래픽·리소스 산정 방법

기준일: 2026-09-14. [설계안](GHeSS_솔루션_재설계.md)의 용량 계획이며, 실제 부하 시험이나 구매 확정 사양이 아니다. 결과표는 [산정 결과](산정_결과.md), 입력은 [inputs.json](../capacity/inputs.json), 계산은 [estimate.py](../capacity/estimate.py)에 있다.

## 1. 확정 입력과 중요한 해석

| 입력 | 사용 값 | 근거·해석 |
|---|---:|---|
| 일일 사용자 | 약 1,500명 | 사용자 예상. 08~18시 누적 이용자로 해석; 1,500 동시접속이 아님 |
| 이용 시간 | 10시간/일 | 08:00~18:00 |
| 문서 | 약 61,000건 | 사용자 정정. 실제 논리 문서 ID·개정별 파일 개수는 별도 집계 필요 |
| 파일 크기 | 약 95GB | **DeDRM 완료 문서 전체 크기**. DRM 해제 시간은 현재 산정에서 제외 |
| 현재 처리 | 파싱·이미지 추출·PaddleOCRv5·청킹·임베딩·Milvus 적재 | 이미 진행된 구현을 재사용. 아래 전량 재처리는 비교를 위한 계산 |

평균 파일 크기는 `95GB / 61,000 ≈ 1.56MB`다. 이것으로 페이지 수, OCR 이미지 수, 토큰 수, 벡터 수를 역산할 수 없다. 작은 Office 파일도 많은 텍스트를 담고, 이미지 압축률·표·중복·청크 overlap은 서로 다르기 때문이다.

GB=10^9 bytes, MB=10^6 bytes, GiB=2^30 bytes로 표기한다. 사용자가 말한 95GB가 실제로 95GiB였다면 `source_gb`를 약 102.01로 수정한다. 사내 모델 사양은 공개 모델과 같다고 가정하지 않는다.

## 2. 온라인 트래픽과 모델 요구량

### 2.1 시나리오 입력

사용자 수는 모두 1,500명으로 고정하고 활동량과 집중도를 바꾼다.

| 가정 | 낮음 | 기준 | 높음 |
|---|---:|---:|---:|
| 1인당 질문/일 | 3 | 5 | 10 |
| 피크/10시간 평균 배수 | 3 | 5 | 8 |
| GLM 답변을 생성하는 질문 비율 | 65% | 75% | 85% |
| 생성 질문당 평균 GLM 호출 | 1.02 | 1.05 | 1.10 |

생성을 생략하는 비율에는 문서번호 조회·검색 목록·기존 요약 재사용·근거 부족이 포함된다. 실제 측정 없이 캐시 적중률을 크게 잡지 않았다. 생성 비율이 100%이면 기준 시나리오보다 모델 요구량이 약 33% 증가한다.

공통 가정은 입력 평균 4,000토큰/호출, 출력 평균 400토큰/호출, 평균 첫 토큰 대기 5초, 출력 속도 16 tok/s, 목표 이용률 70%다. **이 값들은 GLM-5.3-Flash의 실제 사내 성능이 아니다.** 모델·프롬프트·부하별로 측정해 교체한다.

### 2.2 산정식

```text
Q_day       = 일일 사용자 × 1인당 질문 수
λ_query     = Q_day / (이용 시간 × 3600) × 피크 배수       [질문/초]
λ_model     = λ_query × 생성 비율 × 생성 질문당 평균 호출 [호출/초]
S_model     = 평균 TTFT + 평균 출력 토큰 / 평균 출력 tok/s [초/호출]

필요 동시 모델 슬롯 = ceil(λ_model × S_model / 목표 이용률)
필요 RPM 배정      = ceil(λ_model × 60 / 목표 이용률)
필요 입력 TPM      = ceil(λ_model × 60 × 입력 토큰 / 목표 이용률)
필요 출력 TPM      = ceil(λ_model × 60 × 출력 토큰 / 목표 이용률)
```

기준 결과는 하루 7,500질문, 피크 62.5질문/분, 모델 49.21875호출/분이다. 실제 피크 토큰 수요는 입력 196,875 + 출력 19,687.5 = 216,562.5 TPM이다. 이용률 70%로 운용하려면 배정은 **입력 281,250 + 출력 28,125 = 합산 309,375 TPM**, **71 RPM**, **36개 동시 호출** 이상이 필요하다. 토큰이 분리 제한인지 합산 제한인지에 따라 해당 계약을 적용한다.

이용률을 70%로 둔 요구량은 이미 여유를 포함한다. `수요 × 1.3`과 `수요 / 0.7`은 다르며, 여기서는 후자를 사용했다. 모델 공급자와 협의할 값은 시스템 전체 쿼터가 아니라 **타 서비스와 배치 몫을 제외한 온라인 전용 배정량**이다.

Little의 법칙 형태인 `평균 처리 중 호출 수 ≈ 도착률 × 평균 점유 시간`에 여유를 둔 계획식이다. 평균 서비스 시간으로 p95 응답 지연을 보장할 수 없다. 동시 호출 증가에 따라 모델 속도가 느려지거나 공유 GPU 대기가 생기면 같은 식에 동시 부하별 실측 시간을 다시 넣어야 한다.

생성 시간을 가정한 동시성 민감도에서 기준 시나리오는 평균 15초일 때 18슬롯, 30초일 때 36슬롯, 60초일 때 71슬롯, 90초일 때 106슬롯이다. 출력 토큰 감소는 점유 시간을 줄이지만 입력 TPM이 병목이면 효과가 작다.

### 2.3 실제 배정량으로 서비스 한도 역산

```text
μ_model = 목표 이용률 × min(
    동시 호출 한도 / S_model,
    RPM 한도 / 60,
    입력 TPM 한도 / (60 × 입력 토큰),
    출력 TPM 한도 / (60 × 출력 토큰),
    합산 TPM 한도 / (60 × (입력 토큰 + 출력 토큰))
)  # 실제 계약에 존재하는 한도만 사용

지원 가능한 질문 QPS 상한 = μ_model / (생성 비율 × 평균 호출 횟수)
지원 가능한 일일 사용자 상한 = 질문 QPS × 이용 초 / (피크 배수 × 1인당 질문 수)
```

`allocated_limits`의 `null`은 미확인이고 `0`은 사용 불가다. 미확인 한도를 무한대로 보고 “가능” 판정을 내리지 않는다. 일부 한도만 입력한 결과는 그 제약들로 얻은 **상한**이며, 아직 확인하지 않은 제약으로 더 낮아질 수 있다.

사내 모델이 최대 출력 토큰으로 예약량을 계산하거나 추론 토큰도 TPM에 포함하면 400토큰 평균으로 admission을 정하면 안 된다. 호출 시 실제 예약 기준을 사용하고 계산기의 입력값을 그 기준으로 보정한다. 재시도·실패·배치 호출도 집계한다. 사용자별 질문 수 제한보다 먼저 검색 결과 제공·생성 선택·짧은 답변으로 생성 비율을 조절한다.

## 3. FastAPI·검색 API·네트워크

### 3.1 HTTP 동시 처리와 모델 동시 호출의 차이

```text
평균 생성 요청 시간 = 평균 모델 시간 × 호출 계수 + 그 외 처리 시간
평균 요청 시간 = 생성 비율 × 평균 생성 요청 시간
                 + (1 - 생성 비율) × 비생성 요청 시간
HTTP 처리 중 요청 기대값 = 피크 QPS × 평균 요청 시간
계획 HTTP 처리 슬롯 = ceil(기대값 / 목표 이용률)
```

계산기는 모델 외 생성 처리 3초, 비생성 요청 2초를 예로 사용한다. 기준에서 평균 처리 중 HTTP 요청은 약 27.5개, 계획 슬롯은 40개다. 이는 **HTTP 요청 수**이며 열린 로그인 세션 수나 SSE 연결만의 수가 아니다. 장기 연결·큐 대기는 별도 부하 시험에 포함한다. 메모리·연결 풀·파일 디스크립터·LB 제한을 함께 확인한다.

예를 들어 실제 Python CPU 시간이 질문당 0.08 core-second이면 기준 피크의 CPU 수요는 약 0.083 core이고 이용률 60% 적용 시 0.139 core다. 이 값은 I/O 대기를 제외한 **가상 계산 예시**다. CPU 수요가 작아도 HA·런타임·피크·배포를 위해 서비스는 최소 2인스턴스부터 검증한다. 1,500명이라는 사용자 수에 비례해 API 프로세스를 1,500개 만드는 방식은 사용하지 않는다.

### 3.2 검색 서비스 호출량

| 경로 | 기준 피크 상한 계산 | 비고 |
|---|---|---|
| G-HeSS 검색 API | 기본 62.5회/분, 최대 2회/질문이면 125회/분 | 기존 다른 화면의 트래픽과 합산해야 함 |
| Milvus | 최대 2검색/질문이면 125검색/분(2.083 QPS) | 전역 검색 + ES 문서 후보 보완 검색 |
| 질의 임베딩 | 최대 62.5회/분 | 문서번호 조회 등은 생략 가능 |
| 질의 임베딩 토큰 | 256토큰/질문 예시에서 최대 16,000 TPM 수요 | 사내 실제 질문 길이·임베딩 토크나이저로 보정 |

온라인 질의 임베딩과 배치 임베딩이 같은 endpoint이면 온라인용 TPM·동시성을 먼저 남긴다. 인덱스 검색 QPS가 낮아 보여도 ACL 필터·큰 컬렉션 load·OCR 중복·인덱스 상태가 지연을 지배할 수 있다. 문서마다 API를 반복 호출하는 구현은 위 상한을 깨므로 금지한다.

채팅 응답을 출처 포함 100KiB로 가정하면 기준 피크 응답 대역폭은 약 0.85Mbps다. 반면 평균 1.56MB 문서를 분당 100회 다운로드하면 약 20.8Mbps다. 이미지 원본 다운로드, PDF 미리보기, 파서가 만드는 페이지 렌더링, 초기 파일 이동이 네트워크·객체 저장소 부하를 좌우할 수 있으므로 채팅 텍스트와 분리한다.

## 4. Milvus 메모리와 저장소

### 4.1 실제 통계가 시나리오보다 우선

첫 확인값은 **현재 유효 청크/벡터 수, 차원·dtype, ANN 종류·파라미터, scalar 필드 크기, loaded collection/partition, query replica 수, 실사용 메모리와 인덱스 크기**다. 실제 벡터 수가 있으면 아래 `N` 계산을 그것으로 대체한다. 본문/OCR 청크를 따로 집계해 총합을 맞춘다.

| 가정 | 작은 문서 | 기준 | 큰 문서 |
|---|---:|---:|---:|
| 문서당 페이지 | 10 | 20 | 40 |
| 페이지당 청크(본문+OCR+overlap 결과 전체) | 2 | 3 | 4 |
| 문서당 청크 | 20 | 60 | 160 |
| 벡터 수 | 122만 | 366만 | 976만 |

세 시나리오는 현재 Milvus가 이 수량이라는 주장이 아니다. 한 이미지에서 여러 OCR 청크가 나오거나 페이지보다 이미지가 훨씬 많으면 실제 수량은 이 범위를 벗어날 수 있다. 계산기에서는 `pages_per_document × chunks_per_page`가 문서당 총청크이므로 실제 통계를 넣어 보정한다.

### 4.2 메모리 산정식

```text
N = 문서 수 × 문서당 페이지 × 페이지당 청크
벡터 원시 bytes = N × 임베딩 차원 × 차원당 bytes

질의 복제본당 RAM GiB =
  (원시 벡터 bytes × resident 계수 + N × scalar bytes/청크)
  / 2^30 / 메모리 목표 이용률 + 프로세스 여유 GiB
전체 질의 RAM = 복제본당 RAM × query replica 수
```

예시 계수는 float32 1,024차원, resident 2.0, scalar 1KiB/청크, 메모리 이용률 70%, 복제본별 프로세스 여유 8GiB, 질의 복제본 2개다. resident 2.0은 원시 벡터 외 인덱스/복사/오버헤드를 위한 **계획 가정**으로 Milvus 공식 고정 배수가 아니다. scalar의 긴 본문·ACL 목록·동적 필드가 크면 늘려야 한다.

기준에서 원시 벡터는 약 14.0GiB, 복제본당 RAM은 약 52.9GiB다. 현재 개정만 메모리에 load하는 가정이다. 이력 30%를 추가 load하면 약 66.3GiB로 늘며, 같은 크기의 새 세대 인덱스를 동시에 load하면 약 97.8GiB까지 증가할 수 있다. 따라서 **운영 64GiB가 가능하더라도 재색인 중 동일 노드 메모리는 부족할 수 있다.** 전체 컬렉션 단위 load 여부와 이력 분리가 불가능한 현재 구조라면 실제 loaded row 수로 바로 계산한다.

복제본당 RAM은 한 물리 서버의 의무 사양이 아니라 해당 복제본의 전체 query 자원 합계다. 샤드 수를 늘린다고 벡터 전체 메모리가 자동으로 줄지 않는다. HNSW가 아닌 인덱스·압축·mmap·디스크 방식은 각각 recall/latency/IOPS를 측정한 뒤 다른 계수를 사용한다. [Milvus HNSW](https://milvus.io/docs/hnsw.md), [질의 복제본](https://milvus.io/docs/replica.md).

### 4.3 저장소의 서로 다른 계수

| 항목 | 예시 산정 | 범위 |
|---|---|---|
| 원본·파생 자산 | (DeDRM 95GB + 추출 자산 95GB × 비율 + 정규화 텍스트) × 1.3 | 자산 비율 0.5/1/2, 정규화 텍스트 2KiB/청크 |
| Milvus 논리 영속 데이터 | (원시 벡터 × 2.0 + scalar 1KiB/청크) × 1.3 | persisted 계수는 원시 벡터와 생성 인덱스의 예산 가정 |
| 키워드 색인 | 청크 수 × 3KiB × 저장 복사본 2 × 1.3 | 전체 서비스 비교용. G-HeSS API 재사용이면 기존 시스템 소유 |
| 문서 메타 DB | (청크 수 × 768B + 문서 수 × 4KiB) × 1.3 | 텍스트 본문은 산출물 저장소에 있다고 가정, 대화·로그 제외 |
| 추가 재색인 | Milvus + 키워드 색인 1세트 | 벡터 재계산 여부와 무관하게 생성 가능한 추가 인덱스 공간 |
| 독립 백업 | 상시 저장 전체 1세트 | 보수적 예산. 실제 스냅샷/중복 제거 정책으로 조정 |
| 빈 공간 | 위 합계 / 0.7 | 할당 공간 중 30%를 비워둠 |

1.3은 **입력 스냅샷 대비 추가 개정 보유 여유**다. 이미 95GB 안에 들어 있는 과거 개정을 다시 “현재의 30%”로 세는 것이 아니라 추가 보유를 위한 계획량이다. 실제 보유 기간·개정량이 확인되면 이 계수를 교체한다. 추출 이미지가 이미 95GB에 함께 포함돼 있다면 추가 자산 비율에서 중복을 제거해야 한다.

기준 합계는 상시 약 310.9GiB, 재색인 추가 68.1GiB, 독립 백업 310.9GiB, 빈 공간 포함 논리 할당 약 **985.5GiB**다. 작은/큰 문서에서는 각각 약 602.9/1,859.7GiB다. 이것은 여러 저장소를 더한 계획값이며 단일 Milvus 디스크 요구량이 아니다.

Milvus query replica=2는 query 메모리의 복제 계수이며 Milvus 객체 저장 전체를 다시 두 배 하는 계수가 아니다. 반면 객체 저장소의 실제 EC/복제, WAL/메시지 로그, 인덱스 빌드·compaction 임시공간, 스냅샷 보유, 장애 시 복구 공간은 별도다. 설치 버전/배포의 종속 서비스를 확인한다. [Milvus 종속 서비스](https://milvus.io/docs/scale-dependencies.md).

G-HeSS API 재사용 시 신규 키워드 색인 저장량은 0일 수 있다. 위 표의 키워드 항목을 신규 개발 서버 요청에 그대로 더하지 않는다. 기존 원본·파싱 산출물·Milvus 공간도 이미 할당된 만큼 차감한다. 물리 디스크 구매량은 각 저장소 소유자가 복제/EC·로그·백업 정책으로 변환해야 한다.

## 5. 전체 재처리와 일일 증분

현재 데이터는 이미 적재되어 있으므로 새 설계의 선행 조건이 전량 재처리는 아니다. 텍스트가 그대로인 메타·검색·인덱스 변경은 벡터 재사용을 먼저 검토한다. 아래는 청킹/임베딩 정책을 전면 바꾸었을 경우와 증분 처리 용량을 비교하는 예시다.

### 5.1 처리량 가정

| 단계 | 예시 가정 | 실제 필요한 값 |
|---|---|---|
| 파일 읽기 | 50MB/s | 공유 스토리지 읽기·동시 사용 시 throughput |
| 파싱 | 페이지당 0.2 CPU초, 8 core | 형식별 wall time/CPU time, 최대 RSS, 실패율 |
| OCR | 페이지 30%가 OCR 작업 1개에 해당, 작업당 2 CPU초, 8 core | **실제 이미지 개수와 해상도별 이미지/초**, GPU 사용 여부 |
| 임베딩 | 최대 40청크/초, 2,000,000 TPM | 호출 batch·TPM·최대 입력·동시성 중 최솟값 |
| 색인 | 500청크/초 | insert·flush·index build·load 각각의 처리량 |
| 유효 처리 효율 | 70% | 직렬 구간·I/O·실패·재시도 반영 |
| 배치 시간 | 14시간/일 | 18~08시 예시. 야간에 쿼터 사용 가능하다는 확인은 없음 |

OCR 계산은 현재 이미지 개수가 없어서 쓰는 페이지 환산치다. PaddleOCRv5의 공개 벤치마크를 사내 CPU/GPU의 성능으로 적용하지 않았다. 실제 이미지 수를 `I`, 평균 OCR 서비스 시간을 `S_img`, 작업 슬롯을 `C`라 하면 `OCR 시간=I×S_img/(C×효율)`로 대체한다. 여러 프로세스가 같은 GPU를 쓰면 `C`배 속도 향상을 가정하지 않고 합산 실측 throughput을 쓴다.

```text
임베딩 유효 청크/초 = min(측정 청크/초, TPM / (60 × 청크당 입력 토큰)) × 효율
단계별 시간 = 처리할 작업량 / 단계별 유효 처리량
완전 중첩 하한 = 가장 느린 단계의 시간
완전 직렬 환산 = 단계별 시간의 합
```

기준 366만 청크 × 400토큰이면 전량 임베딩 입력은 약 **14.64억 토큰**이다. 가정상 파싱 12.1시간, OCR 36.3시간, 임베딩 36.3시간, 색인 쓰기 2.9시간이며, 모든 단계가 별도 자원으로 완전히 중첩되면 최소 약 2.6배치일, 직렬 환산은 약 6.3배치일이다. 이 둘은 보장 구간이 아니다. 인덱스 빌드/load, 불균등 파일, 수동 확인, 외부 서비스 혼잡으로 더 길어질 수 있다.

CPU 파싱과 OCR을 같은 8 core에서 돌린다면 각자 8 core로 계산한 중첩 하한을 사용할 수 없다. CPU 요구 시간을 합쳐 공유 코어로 나누고 스케줄링을 반영해야 한다. GPU OCR·동시 임베딩도 공유 자원인 경우 동일하다.

일일 변경량은 미확인이므로 300건/일을 예시로 뒀다. 기준 분포와 같다면 18,000청크, 임베딩 입력 720만 토큰/일이며 병목 단계 약 0.18시간이다. 작은 증분의 준비·flush·인덱스 고정비와 변화량 편차는 전량의 단순 비례로 추정할 수 없으므로 별도 측정한다.

전 문서 요약·VLM 처리는 계산에 포함하지 않았다. 61,000문서에 단순히 1회씩 30초 생성만 해도 모델 점유 508시간이다. 배치 4슬롯·효율 70%이면 약 181.5시간, 14시간 배치로 약 13일이다. 긴 문서 전문 요약은 여러 분할 호출과 통합이 필요하므로 더 크다. 기본 검색을 모든 문서의 요약 완료까지 기다리게 하지 않는 이유다.

## 6. 초기 자원 요청안

아래는 구매 확정안이 아니라 **검증을 시작할 역할별 예산**이다. 현재 서버/공유 자원을 먼저 확인하고 필요한 차이만 요청한다.

| 역할 | 검증 시작 자원 | 확장 근거·제외사항 |
|---|---|---|
| FastAPI | 2개 인스턴스 × 2~4 vCPU / 4~8GiB | SSE·연결 풀·CPU·장애 시 한 대 처리량. GLM 쿼터와 별개 |
| 파싱 작업자 | 합계 8 vCPU / 16~32GiB | 현재 파서 최대 RSS, 큰 파일 격리. 증분만이면 낮출 수 있음 |
| OCR 작업자 | CPU 합계 8 vCPU / 16~32GiB 비교 시작 | 현행 GPU 사용 시 그 측정값 재사용. GPU 장수는 모델/해상도 실측 전 미산정 |
| Milvus query | 기준 가정에서 복제본당 64GiB급, 총 2복제본 검토 | CPU는 복제본당 8~16 vCPU 실측 출발점. 전체 replica의 합산 RAM임. 이력/새 세대 동시 load 시 96~128GiB급 또는 추가 노드 검토 |
| Milvus data/index 등 | 임시 8~16 vCPU / 16~32GiB 추가 예산 검토 | 설치 버전·현재 배포·인덱스 빌드에 따라 다름. query 메모리에 포함되지 않음 |
| 메타/작업 RDB | 4 vCPU / 16GiB급 primary 실측 | 사내 기존 DB 우선. standby/백업/로그/연결 제한 별도 |
| 전역 limiter/큐 | 기존 사내 서비스 우선 | 미제공 시 별도 HA/운영계약 설계; FastAPI 메모리만으로 다중 인스턴스 한도 관리 금지 |
| 검색 API | 신규 ES 서버 배정은 우선 보류 | 기존 API의 추가 63~125요청/분 + 기존 트래픽 처리 가능 여부 확인 |
| 객체/인덱스/백업 | 전체 논리 예산은 시나리오표 사용 | 기존 자원 차감, 물리 복제·EC·로그·임시공간 별도 |
| GLM | 사내 서비스의 온라인 배정량 협의 | 애플리케이션 GPU로 추론 서버를 새로 산정하지 않음 |

Milvus가 standalone이면 query replica 2개 계획이 그대로 적용된다고 가정하지 않는다. distributed/managed 여부와 지원 기능·종속 서비스 HA를 확인한다. etcd, 메시지/WAL 계층, 객체 저장소, proxy/coordination 등 설치 버전에서 필요한 역할의 가용성을 빠뜨리지 않는다. 이 표의 역할은 물리 서버 대수나 Kubernetes pod 목록과 1:1이 아니다.

로그도 별도 예산이다. 예를 들어 질문당 감사/메타 20KiB × 하루 7,500질문 × 30일은 압축·복제 전 약 4.3GiB다. 프롬프트·원문·토큰 이벤트를 전부 저장하면 크게 증가한다. 기본은 본문 없는 지표·식별자이며 민감한 평가 샘플은 분리한다.

## 7. 실측으로 산정값을 확정하는 절차

### A. 먼저 받아야 할 현재 통계

- Milvus: 버전/배포 형태, 컬렉션 schema, 임베딩 모델/차원/dtype, index params, shards, replicas, load 상태, 현재/이력/삭제/중복을 구분한 벡터 수, resident RAM, 데이터·인덱스 크기.
- 파서·청커: 포팅 기준 커밋, 문서당 청크 p50/p95/p99, 문자·토큰 단위, overlap, 원문 대비 파싱 실패율, OCR 결과 포함 여부·중복 비중.
- OCR: 실제 rec/det 모델과 언어 설정, 총 이미지 수·해상도·파일별 이미지 수, 이미지당 wall/CPU time, CPU/GPU 메모리, 한글·숫자 인식 오류 표본.
- 사내 GLM/임베딩: API 형식, 입력·출력 상한, streaming/thinking 지원, 취소 동작, 동시/RPM/TPM 제한, 공유 범위·야간 이용 가능량, usage 집계 기준.
- G-HeSS 검색 API: 문서 ID/개정/권한/필터/페이지 계약, p95·추가 트래픽 한도. API 호출을 실행하지 않고 현재는 계약 항목만 정의했다.

### B. 성능 실험 매트릭스

| 실험 | 설정 | 기록·판단 |
|---|---|---|
| GLM 단독 | 입력 2k/4k/6k, 출력 200/400/600토큰, 동시 1/2/4/8 이후 허용 쿼터 내 확대 | TTFT·출력 tok/s·전체 p50/p95/p99·429·usage. 설정 조합당 최소 30회는 1차 진단용 |
| 검색 단독 | 현재 적재 전체 데이터, 현재 ANN 설정, API-only/Milvus-only/통합 | Recall@10, 필터 선택도, 문서번호/OCR별 품질, 호출 횟수·p95 |
| 요청 혼합 | 0.375 / 1.042 / 3.333 QPS, 정해진 질문 mix | 10분 예열 후 30분 유지, 기준 2시간 안정성, 별도 2배 burst |
| 공급자 장애 | 429·timeout·연결 해제·느린 stream, 생성 중 취소 | 대기열/토큰 예약 누수, 재시도 증폭, 검색 전환 확인 |
| 적재와 검색 동시 | 일상 증분 및 선택적 재색인 각각 | query p95, CPU/RAM/IOPS, segment/index build/load와 경쟁 |
| 파이프라인 | 유형·크기별 샘플 → 큰 파일 포함 1,000건 선택 재처리 | 성공·실패·부분 완료, 중복, 처리량, 출처 위치, 재개 |

사내 승인된 검증 환경/할당량에서 수행할 계획이다. 모델 쿼터를 모르는 상태에서 높은 동시 호출을 실행하는 지시가 아니다. 현재 세션에서는 사내 서비스 호출이나 실제 부하 시험을 수행하지 않았다.

QPS 고정 유입(open-loop)과 동시 사용자(closed-loop) 실험을 구분한다. 응답이 느려져 테스트 클라이언트의 유입도 줄어드는 현상이 과부하를 가리지 않게 한다. 표본 수, 테스트 시간, warm/cold 상태, 동시에 돌던 배치를 결과에 기록한다. 30회 진단에서 계산한 p99를 운영 보장으로 삼지 않는다.

### C. 결정 기준

1. 현재 인덱스가 전체 데이터+실제 필터에서 검색 p95 3초 목표와 recall 목표를 만족하면 샤드·ANN을 유지한다.
2. 낮은 recall은 청크/언어/OCR/문서·청크 병합을 먼저 구분한다. RAM 부족이나 큐 적체 문제를 프롬프트로 해결하려 하지 않는다.
3. 기본 경로의 생성 비율·입출력 토큰을 측정해 산정 입력을 교체한다. 모델 70% 이용률 예산에서도 p95 60초 목표가 안 되면 문장 길이/생성 비율/할당량을 조정하고 다시 검증한다.
4. 전체 재처리 대신 `필터 변경 → 메타 보강 → 대상 OCR/청크 수정 → 인덱스 재구성 → 전량 임베딩 변경` 중 가장 작은 필요한 범위를 선택한다.
5. 모든 실제값·기간·환경·소스 버전을 입력 파일의 provenance와 함께 기록하고 계산 결과를 재생성한다.

## 8. 계산기 검증과 한계

계산기는 쿼터 미확인과 0을 구분하고, 출력 TPM이 동시 호출 한도보다 먼저 병목이 되는 경우, query replica가 RAM만 배수로 늘리는 관계, 임베딩 토큰 한도, 작업량 0, 잘못된 입력, 기준 수작업 계산을 테스트한다. 부동소수점 정수 경계의 올림 오차도 처리한다. 외부 의존성·네트워크 호출은 없다.

```bash
python3 -m unittest discover -s capacity -v
python3 capacity/estimate.py --output docs/산정_결과.md
```

단순 용량 계획기이므로 큐잉 지연 분포, GPU continuous batching, Milvus 내부 저장 압축, 인덱스 빌드/load 시간, 페이지별 OCR 이미지 분포, 물리 저장 복제/EC를 시뮬레이션하지 않는다. 실제 측정값으로 계산 계수를 교체하고 혼합 부하 시험으로 확정해야 한다.
