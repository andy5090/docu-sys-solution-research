# 1차 오픈 용량 계획: 09~18시 1,500명

> 범위 갱신(2026-09-30): 이 문서는 검색·짧은 답변 중심의 과거 비교안이다. 파일 첨부·DeDRM·DOCX/PPTX 생성 포함, Milvus 제외 최신 보수 산정은 [권장 서버 용량 추정](권장_서버_용량_추정.md)과 [DOCX](권장_서버_용량_추정.docx)를 따른다. 두 안의 자원을 합산하지 않는다.

기준일: 2026-09-29. 사용자 요청의 운영 시간을 **09~18시, 9시간**으로 반영했다. 1,500명은 일일 이용자로 해석한다. 질문 빈도·피크·모델 속도·CPU/RAM은 실측 전 계획 가정이며, 아래 사양으로 처리량이나 가용성이 검증된 상태는 아니다.

## 1. 트래픽 준비 목표

| 구분 | 가벼운 사용 | 기준 사용 | 높은 사용 |
|---|---:|---:|---:|
| 1인당 하루 질문 | 3회 | 5회 | 10회 |
| 하루 질문 | 4,500건 | 7,500건 | 15,000건 |
| 9시간 평균 질문/초 | 0.139 | 0.231 | 0.463 |
| 피크 배수 가정 | 3배 | 5배 | 8배 |
| 피크 질문/초 | 0.417 | 1.157 | 3.704 |
| 피크 질문/분 | 25.0 | 69.4 | 222.2 |

`피크 질문/초 = 1,500 × 1인당 하루 질문 ÷ 32,400 × 피크 배수`.

평상시 피크 약 1.2질문/초, 높은 사용량 약 4질문/초를 예상 범위로 두고, **준비 목표는 5질문/초**로 잡는다. 오픈 공지 후 1,500명이 5분 동안 한 번씩 질문하면 5질문/초다. 1분에 몰리면 25질문/초이므로 공지·교육을 분산하거나 입장 대기를 적용할 별도 집중 시나리오가 필요하다. 5질문/초 시험 통과가 25질문/초 수용을 뜻하지 않는다.

질문 한 건은 RAG 요청 한 건이다. 로그인·화면 조회·문서 다운로드·이미지 미리보기·장기 SSE 연결은 별도로 계측한다. 5질문/초에서 질의 임베딩은 최대 5회/초, Milvus와 G-HeSS 검색 API는 각각 최대 2회/질문이면 10회/초다. G-HeSS의 기존 트래픽과 온라인/배치 임베딩의 공유 한도를 합산한다.

## 2. 초기 자원 및 레플리카

| 구성 요소 | 개별 자원 시작값 | 개수·운영 조건 |
|---|---|---|
| FastAPI | **2 vCPU / 4GiB** | **3레플리카**, 최대 6개 확장 검토. 서로 다른 노드에 배치하고 한 개 중단 시 검증 |
| Milvus 검색 계층 | **복제본 그룹당 16 vCPU / 128GiB** | **query replica 2개**, Distributed/managed 지원 및 역할별 장애 대응 확인 |
| 메타데이터·작업 DB | 4 vCPU / 16GiB | primary 1 + standby 1. 기존 사내 서비스 우선 |
| Redis | 2 vCPU / 4GiB | 기존 HA 서비스 우선. 신규 구성 시 데이터 복제·장애 감지·승격 토폴로지 별도 확정 |

**FastAPI와 Milvus 검색 계층의 합계는 38 vCPU / 268GiB**다. 이는 전체 시스템 총량이 아니다. Milvus data/index·proxy/coordination·etcd/WAL·객체 저장소, DB/Redis, 임베딩 추론, OCR/파싱, 백업과 노드 OS·운영 자원은 별도다. 역할별 추가 예산은 [산정 방법](트래픽_리소스_산정.md#6-초기-자원-요청안)을 따른다.

이 API 사양은 GLM·질의 임베딩 추론 및 OCR을 API 프로세스 밖에서 처리하는 전제다. 임베딩 서버를 자체 운영한다면 모델·입력 길이·CPU/GPU별 지연을 측정해 별도 배정한다. Kubernetes에서 컨테이너당 Uvicorn 프로세스 하나로 시작하고 레플리카로 확장할 수 있다. CPU뿐 아니라 활성 요청·대기열·이벤트 루프 지연을 관측하되, 공급자 병목만으로 API가 무한 확장되지 않도록 상한을 둔다. [FastAPI 배포 문서](https://fastapi.tiangolo.com/deployment/docker/#one-process-per-container)

Milvus는 확인된 **7,585,436개 청크**, BGE-M3 표준 dense 1,024차원·float32 가정에서 원시 벡터만 약 **28.94GiB**다. [계산기](../capacity/estimate.py)의 인덱스·scalar·여유 가정으로 복제본당 약 **101GiB**이므로 **128GiB**를 검증 시작점으로 둔다. 이전 64GiB 추정치는 현재 청크 수의 준비 기준으로 사용하지 않는다. 구·신 컬렉션 동시 load와 index build peak는 추가 측정한다.

Milvus replica group은 전체 검색 데이터의 복사본을 보유하는 QueryNode 그룹이다. 여러 노드로 나뉠 수 있으며 표는 그룹 전체의 자원 합계다. Standalone 인스턴스를 단순 복제해 같은 구성이 된다고 가정하지 않는다. 두 복제본을 서로 다른 장애 영역에 두고, 하나가 불능일 때 남은 그룹이 목표 부하를 처리하는지 확인한다. 검색 복제본만으로 Milvus 전체의 HA가 완성되지는 않는다. [Milvus 복제본 문서](https://milvus.io/docs/replica.md)

## 3. GLM 배정량이 수용량을 제한한다

[자동 계산 결과](산정_결과.md)의 기준 시나리오는 생성 비율 **75%**이며, 9시간 기준 동시 호출 40개·79 RPM·합산 343,750 TPM이다. 아래 오픈 준비 계산은 생성 비율을 아직 모르므로 **전 질문 생성(100%)**을 가정한 별도 조건이다. 평균 호출 횟수 1.05는 추가 호출의 예산 가정이며 재시도를 무조건 허용한다는 뜻이 아니다.

- 질문당 평균 모델 호출 1.05회, 호출당 입력 4,000·출력 400토큰.
- 계획 이용률 70%. 배정량은 수요를 0.7로 나눠 이미 여유를 반영했다.
- 모델 평균 점유 시간 30초 또는 60초. 사내 GLM의 실측 속도가 아니다.

| GLM 온라인 배정량 | 기준 피크 1.157질문/초 | 준비 목표 5질문/초 |
|---|---:|---:|
| 평균 30초일 때 동시 호출 | **53개** | **225개** |
| 평균 60초일 때 동시 호출 | **105개** | **450개** |
| 분당 호출 한도 RPM | **105 이상** | **450 이상** |
| 입력 TPM | 416,667 이상 | 1,800,000 이상 |
| 출력 TPM | 41,667 이상 | 180,000 이상 |
| 합산 TPM | **458,334 이상** | **1,980,000 이상** |

TPM 분리/합산은 제공자의 실제 계약에 맞게 적용한다. 동시성·RPM·TPM은 함께 충족해야 하며, 타 서비스·배치 몫을 제외한 온라인 배정량이어야 한다. 공급자가 최대 출력 토큰이나 추론 토큰까지 예약하면 그 기준으로 다시 계산한다.

예를 들어 동시 호출 20개·평균 점유 30초라면 동시성으로 얻는 지원 상한은 `20 × 0.7 ÷ 30 ÷ 1.05 ≈ 0.44질문/초`다. RPM/TPM 제약이 있으면 더 낮아진다. 기준 피크에도 부족하므로 API 레플리카 추가로 해결할 수 없다. 여러 API 인스턴스가 공유하는 전역 limiter, 짧고 유한한 대기열, 검색 결과 우선 제공·생성 선택을 적용한다.

아래 명령은 기존 계산기로 표의 수치를 재현하며 입력 파일을 변경하거나 외부 서비스에 접속하지 않는다. 5질문/초는 동일 하루 7,500질문에 피크 배수 21.6을 적용한 오픈 집중 조건이다.

```bash
python3 - <<'PY'
import json
from pathlib import Path
from capacity.estimate import calculate

data = json.loads(Path("capacity/inputs.json").read_text())
data["online"]["scenarios"] = [
    {"name": name, "questions_per_user": 5, "peak_factor": peak,
     "llm_share": 1, "calls_per_generated_query": 1.05}
    for name, peak in (("전부 생성 기준", 5), ("오픈 준비 5 QPS", 21.6))
]
for row in calculate(data)["online"]:
    print(row["name"], {
        key: row[key] for key in (
            "peak_qps", "slot_sensitivity", "required_rpm",
            "required_input_tpm", "required_output_tpm", "required_total_tpm"
        )
    })
PY
```

## 4. 오픈 전 확정 조건

1. **API:** 모델 지연을 모사해 5질문/초를 30분 유지하고, API 한 개 중단 상태에서도 확인한다. 오류율·p95·메모리·활성 연결·대기열이 안정적인지 기록한다.
2. **검색:** 전체 데이터와 실제 ACL 필터로 Milvus 최대 10검색/초를 시험한다. 한 복제본 불능 상태도 포함하며, [기존 검색 품질·지연 목표](트래픽_리소스_산정.md#c-결정-기준)를 함께 충족해야 한다.
3. **실제 GLM:** 확보한 할당량 범위에서 기준 피크 약 1.2질문/초부터 시험한다. 5질문/초 생성 처리는 위 쿼터 확보와 실측 통과 후 확정한다. 모사 시험만으로 실제 모델 처리량을 보장하지 않는다.
4. **증분 작업:** OCR·파싱·임베딩·Milvus 적재가 검색 자원과 경쟁할 때의 지연을 확인한다. 현재 전량 임베딩 완료 상태를 활용하고 오픈 전에 불필요한 전량 재처리를 추가하지 않는다.

현재 미확인 값은 GLM 실제 평균/p95 응답 시간·동시/RPM/TPM, 임베딩 endpoint 배치 형태·속도, Milvus 버전·인덱스·schema·load RAM·가용 하드웨어다. 사내 서비스 부하 시험이나 인프라 배정은 이번 문서 작성에서 수행하지 않았다.
