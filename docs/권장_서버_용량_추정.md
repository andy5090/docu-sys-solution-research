# G-HeSS AI Agent
## 트래픽 추정에 따른 권장 서버 용량

기준일: 2026-09-29 | 문서 버전: 1.0 | 범위: 1차 오픈 인프라 검토

### 1. 권장안 요약

일일 이용자 약 1,500명, 운영 시간 09:00~18:00을 기준으로 **FastAPI 2 vCPU·4GiB × 3레플리카**, **Milvus 검색 복제본 그룹당 16 vCPU·128GiB × 2개**를 검증 시작 사양으로 권장한다. 두 계층의 합계는 **38 vCPU·268GiB**다. 역할별 할당량이며 물리 서버 5대를 의미하지 않는다.

기준 사용 피크는 **1.157질문/초**, 높은 사용 피크는 **3.704질문/초**다. 초기 준비 목표는 **5질문/초**로 두되, 실제 처리량은 검색·모델·API 혼합 부하 시험을 통과한 뒤 확정한다. CPU 사양은 QPS만으로 도출된 성능 보장값이 아니라 기존 계획의 검증 시작값이다.

| 요청 항목 | 권장 준비량 | 적용 범위 |
|---|---|---|
| API + Milvus 검색 | 38 vCPU / 268GiB | DB·배치·Milvus 보조 서비스·OS 제외 |
| 저장소 | 기준 논리 예산 약 1,336.6GiB | 여러 저장소·백업 합계, 기존 할당분 차감 |
| GLM 기준 사용 | 동시 40개 / 79 RPM / 343,750 TPM | 생성 비율 75%, 평균 모델 점유 30초 |
| GLM 오픈 준비 | 동시 225개 / 450 RPM / 1,980,000 TPM | 5질문/초, 생성 비율 100%, 평균 30초 |

### 2. 입력과 적용 범위

| 항목 | 입력 및 해석 |
|---|---|
| 예상 이용자·운영 시간 | 1,500명/일, 9시간/일. 동시접속 1,500명이 아님 |
| 보유 문서 | DeDRM 완료 약 61,000건, 약 95GB |
| 완료 청크 | 7,585,436개, 2026-09-15 임베딩 대상 전량 완료 |
| 임베딩·유사도 | BGE-M3 / COSINE. 표준 dense 1,024차원 [1] |
| 저장·적재 가정 | float32, 청크당 dense 1개, 전체 검색 데이터 load |

이 문서는 저장소의 확인된 입력과 계획 가정을 구분해 정리한 추정안이다. 사내 GLM 실제 쿼터·서버 벤치마크·Milvus 설치 버전은 미확인이다. GPU 대수, 전체 시스템 물리 서버 대수, 구매 비용은 이 자료만으로 확정하지 않는다. GB=10⁹ bytes, GiB=2³⁰ bytes, TiB=1,024GiB를 사용한다.

## 3. 트래픽 시나리오와 준비 목표

| 지표 | 낮음 | 기준 | 높음 |
|---|---:|---:|---:|
| 1인당 질문/일 | 3 | 5 | 10 |
| 하루 질문 | 4,500 | 7,500 | 15,000 |
| 9시간 평균 QPS | 0.139 | 0.231 | 0.463 |
| 피크 배수 | 3 | 5 | 8 |
| 피크 QPS | 0.417 | 1.157 | 3.704 |
| 피크 질문/분 | 25.0 | 69.4 | 222.2 |
| 생성 답변 비율 | 65% | 75% | 85% |
| 생성 질문당 평균 호출 | 1.02 | 1.05 | 1.10 |

**산정식:** 하루 질문 = 일일 이용자 × 1인당 질문 수. 평균 QPS = 하루 질문 ÷ 32,400초. 피크 QPS = 평균 QPS × 피크 배수. 질문 빈도·집중도·생성 비율은 실측 전 가정이다.

### 오픈 집중 트래픽

1,500명이 5분 동안 질문을 한 번씩 제출하면 5질문/초다. 같은 인원이 1분 안에 제출하면 25질문/초가 된다. 따라서 공지·교육 시간을 분산하고, 유한 대기열과 과부하 시 검색 결과 우선 제공을 준비한다. 5질문/초 시험 통과로 25질문/초 처리까지 보장할 수 없다.

| 연계 서비스 | 5질문/초 준비 시 요구량 | 전제 |
|---|---:|---|
| 질의 임베딩 | 최대 5회/초 | 질문당 1회, 온라인 몫 별도 확보 |
| Milvus 검색 | 최대 10회/초 | 질문당 최대 2회 |
| G-HeSS 검색 API | 최대 10회/초 | 질문당 최대 2회, 기존 트래픽 합산 |
| 생성 HTTP 처리 슬롯 | 약 247개 | 전부 생성, 호출 1.05회·모델 30초·기타 3초, 이용률 70% |

HTTP 처리 슬롯은 프로세스나 CPU 코어 수가 아니다. 위 조건의 평균 처리 중 HTTP 요청은 172.5개이며, 247개는 여유를 둔 계획값이다. 로그인·화면 조회·다운로드·이미지·idle 연결은 이 값에 포함되지 않는다. LB와 애플리케이션의 SSE 활성 연결, 파일 다운로드 대역폭, DB 연결 풀을 별도로 측정한다.

### 트래픽별 운영 방향

낮은 사용 시에도 동일 데이터 전체를 load하므로 Milvus RAM을 질문 수에 비례해 줄이지 않는다. 기준~높은 사용은 동일 시작 사양에서 단계적으로 검증한다. 5질문/초 준비 목표는 한 API 레플리카 또는 한 검색 복제본 그룹 장애가 발생한 경우까지 시험한다. 초과 수요에서는 먼저 모델 쿼터·검색 지연·API CPU 중 실제 병목을 확인한다.

## 4. 역할별 권장 서버 자원

| 역할 | 개별 또는 역할 합계 | 수량·할당 합계 | 운영 조건 |
|---|---|---|---|
| FastAPI | 개별 2 vCPU / 4GiB | 3개, 6 vCPU / 12GiB | 서로 다른 노드, 최대 6개 확장 검토 |
| Milvus query | 그룹당 16 vCPU / 128GiB | 2그룹, 32 vCPU / 256GiB | 전체 데이터 복제, 장애 영역 분리 |
| 메타·작업 RDB | 개별 4 vCPU / 16GiB | primary + standby, 8 vCPU / 32GiB | 기존 사내 DB 우선 |
| Milvus data/index 등 | 역할 합계 8~16 vCPU / 16~32GiB | 추가 임시 예산 | 배포 버전·색인 부하로 보정 |
| Redis limiter·큐 | 개별 2 vCPU / 4GiB | 개수 미확정 | 기존 HA 서비스 우선 |
| 파싱 작업자 | 역할 합계 8 vCPU / 16~32GiB | 별도 배치 예산 | 최대 파일 RSS 확인, 증분 위주 |
| OCR 작업자 | 역할 합계 8 vCPU / 16~32GiB | CPU 비교 시작안 | GPU 사용 중이면 실측값 재사용 |
| 질의·배치 임베딩 | 사내 endpoint 우선 | 자체 운영 시 별도 산정 | 온라인 5회/초와 배치 몫 분리 |
| GLM 생성 | 사내 서비스 이용 | 온라인 쿼터 배정 | 애플리케이션 GPU에 포함하지 않음 |

### 예산 합계의 경계

**필수 검색 경로의 시작 예산은 API + query = 38 vCPU·268GiB**다. 여기에 RDB 두 개와 data/index 임시 예산을 새로 할당한다면 부분 합계는 **54~62 vCPU·316~332GiB**다. 이 역시 Redis, 파싱/OCR, 임베딩, 저장소 서버, proxy/coordination, etcd/WAL, 관측 및 OS 예산을 포함한 전체 시스템 총량은 아니다.

기존 사내 서비스 재사용분은 신규 요청에서 차감한다. 실제 VM·노드 크기는 allocatable 자원과 OS·에이전트 예약량을 확인한 후 정한다. vCPU와 물리 코어는 같은 단위가 아니며 CPU 세대·클럭·메모리 대역폭에 따라 성능이 달라진다.

### 배포와 고가용성

FastAPI는 컨테이너당 Uvicorn 프로세스 하나로 시작하고 레플리카로 확장한다 [3]. 추론·임베딩·OCR은 API 프로세스 밖에서 처리한다. API 한 개 장애 시 남은 2개가 5질문/초를 처리하는지 검증한다. 최대 6개로 확장하면 API 예산은 12 vCPU·24GiB지만, 모델 쿼터는 함께 늘어나지 않는다.

Milvus 복제본 그룹은 하나 이상의 QueryNode로 구성된다 [2]. 표의 128GiB는 그룹 전체 합계다. distributed/managed 지원과 실제 버전을 확인하며 standalone 두 개를 복제본 그룹 두 개로 간주하지 않는다. 검색 복제본뿐 아니라 RDB 승격, Redis 장애 감지·승격, 객체 저장소와 Milvus 종속 서비스까지 검증해야 전체 가용성을 판단할 수 있다.

## 5. GLM 온라인 배정량

호출당 입력 4,000토큰·출력 400토큰, 평균 첫 토큰 5초 + 출력 16 tok/s로 **모델 점유 30초**, 목표 이용률 70%를 가정한다. 이 값은 사내 GLM-5.3-Flash의 측정 성능이 아니다.

| 배정 지표 | 낮음 | 기준 | 높음 |
|---|---:|---:|---:|
| 필요 동시 호출 | 12 | 40 | 149 |
| 필요 RPM | 24 | 79 | 297 |
| 필요 입력 TPM | 94,715 | 312,500 | 1,187,302 |
| 필요 출력 TPM | 9,472 | 31,250 | 118,731 |
| 필요 합산 TPM | 104,186 | 343,750 | 1,306,032 |
| 평균 모델 60초 시 동시 호출 | 24 | 79 | 297 |

위 표는 앞의 시나리오별 생성 비율·호출 횟수를 적용했다. 아래는 생성 비율 **100%**, 생성 질문당 평균 **1.05회**로 통일한 별도 조건이다.

| 전부 생성 조건 | 기준 피크 1.157 QPS | 오픈 준비 5 QPS |
|---|---:|---:|
| 평균 30초 동시 호출 | 53 | 225 |
| 평균 60초 동시 호출 | 105 | 450 |
| 필요 RPM | 105 | 450 |
| 필요 입력 TPM | 416,667 | 1,800,000 |
| 필요 출력 TPM | 41,667 | 180,000 |
| 필요 합산 TPM | 458,334 | 1,980,000 |

**계산 방법:** 모델 호출/초 = 피크 QPS × 생성 비율 × 평균 호출 횟수. 동시 호출 배정 = ceil(호출/초 × 평균 점유 시간 ÷ 0.7). RPM = ceil(호출/초 × 60 ÷ 0.7). 입력·출력·합산 TPM은 각각 해당 토큰 수를 곱해 같은 방식으로 올림한다.

각 배정값에는 이미 70% 이용률 기준 여유가 포함돼 있다. 다시 30%를 가산하지 않는다. 분리 TPM과 합산 TPM은 각각 독립 올림하므로 분리값의 합과 합산값이 1 차이 날 수 있다. 제공자 계약에 맞는 제한을 적용한다.

### 모델 쿼터가 부족한 경우

동시 호출 20개, 평균 30초, 전부 생성·1.05회라면 지원 상한은 20 × 0.7 ÷ 30 ÷ 1.05 ≈ **0.44질문/초**다. RPM·TPM 제약이 있으면 더 낮다. API 증설에 앞서 온라인 할당량 확보, 생성 선택 제공, 출력 길이 조정 및 짧은 대기열을 적용한다.

쿼터는 타 서비스·야간 배치를 제외한 온라인 몫이어야 한다. 모든 API 레플리카가 공유하는 전역 limiter를 두고 동시성·RPM·TPM을 함께 제한한다. 제공자가 최대 출력·추론 토큰으로 예약하면 그 기준으로 재산정한다. 평균 시간으로 계산한 동시성은 p95 응답시간을 보장하지 않는다.

## 6. Milvus RAM과 저장 공간

### 데이터 크기로 산정한 검색 메모리

원시 dense 벡터 = 7,585,436 × 1,024 × 4 bytes ÷ 2³⁰ = **28.94GiB**. scalar 메타데이터는 청크당 1KiB로 약 **7.23GiB**를 가정한다. 인덱스 포함 resident vector 계수 2.0, 메모리 이용률 70%, 프로세스 여유 8GiB를 적용한다.

복제본당 계획 RAM = (28.9361 × 2.0 + 7.2340) ÷ 0.7 + 8 ≈ **101.0GiB**. 이를 올려 **128GiB/그룹**, 2그룹에 **256GiB**를 준비한다. 계수 2.0은 실측 HNSW 오버헤드가 아니라 계획 가정이다. 구·신 컬렉션 동시 load, 인덱스 빌드, growing segment와 sparse/multi-vector 사용은 추가 측정한다.

### 저장소별 기준 시나리오

| 논리 저장 항목 | GiB | 포함 범위 |
|---|---:|---|
| 원본·파생 자산 | 248.8 | 95GB 원본, 추출 자산 원본의 1배, 정규화 텍스트 |
| Milvus 영속 데이터 | 84.6 | 벡터·인덱스·scalar |
| 키워드 색인 | 56.4 | 청크당 3KiB, 복사본 2개 |
| 메타데이터 DB | 7.4 | 청크·문서 메타, 대화·감사 로그 제외 |
| 상시 논리 저장 합계 | 397.3 | 위 네 항목, 추가 개정 여유 1.3배 반영 |
| 재색인 추가 공간 | 141.1 | Milvus + 키워드 인덱스 한 세대 |
| 독립 백업 | 397.3 | 상시 저장 한 세트 |
| 빈 공간 30% 포함 총 할당 | 1,336.6 | (상시 + 재색인 + 백업) ÷ 0.7 |

추출 자산 비율 0.5배/2배를 적용한 범위는 **1,172.2~1,665.2GiB**다. 기준값을 반올림한 논리 준비 예산은 **1.5TiB**, 큰 자산 시나리오는 **2TiB**로 잡을 수 있다. 두 값 모두 개별 서버 디스크 용량이나 물리 디스크 구매 총량이 아니다.

객체 저장소의 복제/EC, WAL, compaction·색인 빌드 임시 공간, 장기 성장, 대화·감사 로그는 별도다. query 복제본 2개를 객체 저장소 전체 용량의 2배로 적용하지 않는다. 기존 G-HeSS API를 재사용하면 키워드 색인의 신규 할당과 관련 백업·재색인 공간을 중복 요청하지 않는다. 기존 원본·벡터 저장량도 실제 사용 가능 공간을 확인해 차감한다.

### 배치와 이관

전량 임베딩은 이미 완료돼 있으므로 기존 벡터 재사용을 우선한다. 일일 변경 300건 가정은 약 37,305청크, 임베딩 병목 약 0.37시간/일이며 준비·flush·인덱스 고정비는 별도다. 야간 14시간·효율 70% 계획을 적용하되 실제 공유 쿼터를 확인한다. 전량 재임베딩 약 75.3시간은 비교용이며 프로덕션 이관 소요 시간이 아니다.

## 7. 용량 확정과 증설 기준

| 검증 항목 | 방법 | 확정·조치 기준 |
|---|---|---|
| API 및 SSE | 10분 예열, 5 QPS 30분, API 1개 중단 | 오류·연결·RSS·큐 추세 확인. 모델 모사와 실제 호출 분리 |
| 검색 | 전체 데이터·실제 ACL, 최대 10검색/초, 복제본 1개 불능 | 검색 p95 ≤3초 및 검색 품질 목표 동시 충족 |
| 실제 GLM | 확보 쿼터 내 기준 1.157 QPS부터 단계 확대 | 일반 생성 p95 ≤60초 목표, 429·TTFT·usage 확인 |
| 안정성·증분 | 기준 부하 2시간, 증분 작업 동시 수행 | 메모리·큐 누적 증가와 검색 지연 악화 여부 확인 |
| 검색 품질·권한 | 문서번호·자연어·OCR·권한 평가 | Recall@10 ≥90% 목표, 권한 밖 노출 0건 |
| 복구 | 장애 전환·백업 복원·이관 복귀 시험 | 측정 RTO/RPO와 운영 요구 비교 후 확정 |

CPU 지속 포화와 이벤트 루프 지연이 원인이면 API를 3→4~6개로 늘려 재시험한다. 모델 대기·429가 원인이면 쿼터와 admission 정책을 조정한다. 검색 load RAM이 계획 70%를 넘거나 OOM 위험이 있으면 실제 메모리 계수·적재 범위를 보정하고 그룹 RAM을 늘린다. 검색 지연은 ACL 필터·ANN 설정·CPU·I/O 병목을 구분한 뒤 증설한다.

실제 Milvus schema·dtype·인덱스·resident RAM, GLM 평균/p95와 할당량, 임베딩 처리량, 기존 스토리지 여유를 확보해야 최종 배정안을 확정할 수 있다. 본 작업에서는 사내 서비스 호출·부하 시험·인프라 배정을 수행하지 않았다.
