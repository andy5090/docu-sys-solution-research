# 트래픽·리소스 계산 결과

기준일: 2026-09-18. `capacity/inputs.json`에서 자동 계산. 실측 성능 또는 구매 확정 사양이 아니다.

입력: 일일 사용자 약 1,500명, 일 10시간, DeDRM 완료 문서 약 61,000건, 파일 약 95GB. 사용자 확인 청크 7,585,436개. GB=10^9 bytes, GiB=2^30 bytes. 나머지는 계획 가정이며 원리와 한계는 [산정 방법](트래픽_리소스_산정.md)을 참조한다.

## 1. 온라인 요청과 모델 쿼터

평균 모델 시간 = 첫 토큰 5초 + 출력 400토큰 / 16 tok/s = 30.0초. 계획 이용률 70%. 질문 수·피크·생성 비율은 시나리오별 가정.

| 지표 | 낮음 | 기준 | 높음 |
|---|---:|---:|---:|
| 하루 질문 | 4,500 | 7,500 | 15,000 |
| 평균 QPS | 0.125 | 0.208 | 0.417 |
| 피크 질문/분 | 22.5 | 62.5 | 200.0 |
| 피크 LLM 호출/분 | 14.9 | 49.2 | 187.0 |
| 하루 LLM 호출 기대값 | 2,984 | 5,906 | 14,025 |
| 피크 입력 TPM 수요 | 59,670 | 196,875 | 748,000 |
| 피크 출력 TPM 수요 | 5,967 | 19,688 | 74,800 |
| 필요 입력 TPM 배정 | 85,243 | 281,250 | 1,068,572 |
| 필요 출력 TPM 배정 | 8,525 | 28,125 | 106,858 |
| 필요 합산 TPM 배정 | 93,768 | 309,375 | 1,175,429 |

필요 배정량에는 계획 이용률 목표가 반영돼 있다. 다시 여유율을 가산하지 않는다. TPM 분리/합산은 제공자의 실제 계약에 해당하는 항목을 사용한다. 동시 호출 슬롯과 HTTP 슬롯은 서로 다른 자원이다.

### 실제 쿼터 입력 상태

- 낮음: 미확인. 처리 가능 여부를 판정하지 않음.
- 기준: 미확인. 처리 가능 여부를 판정하지 않음.
- 높음: 미확인. 처리 가능 여부를 판정하지 않음.

## 2. 문서·Milvus·저장소

세 시나리오 모두 사용자 확인 청크 7,585,436개를 사용한다. 청크당 dense 벡터 1개와 전체 load를 가정하며 이력·삭제·고유 PK 범위는 이관 전에 대사한다. 페이지 수·파생자산 비율은 별도 가정이다.

임베딩 1,024차원, 차원당 4 bytes, 산정 청크 전체를 메모리에 적재, 질의 복제본 2개 가정. 복제본당 RAM은 해당 데이터 전체의 합산값이며 프로세스 여유 8GiB 포함. 차원 입력의 근거는 [산정 방법](트래픽_리소스_산정.md)을 참조한다. 실제 schema 대조가 필요하며 저장 dtype·색인·메모리 계수는 계획 가정이다.

| 지표 | 작은 문서 | 기준 | 큰 문서 |
|---|---:|---:|---:|
| 페이지 (가정) | 610,000 | 1,220,000 | 2,440,000 |
| 청크 (dense 1개/청크 가정) | 7,585,436 | 7,585,436 | 7,585,436 |
| 원시 dense 벡터 GiB | 28.9 | 28.9 | 28.9 |
| Milvus 저장 GiB | 84.6 | 84.6 | 84.6 |
| 질의 복제본당 RAM GiB | 101.0 | 101.0 | 101.0 |
| 복제본 2개 RAM 합계 GiB | 202.0 | 202.0 | 202.0 |
| 원본·파생 자산 GiB | 191.3 | 248.8 | 363.9 |
| 키워드 색인 GiB | 56.4 | 56.4 | 56.4 |
| 문서 메타 DB GiB | 7.4 | 7.4 | 7.4 |
| 상시 논리 저장 GiB | 339.8 | 397.3 | 512.3 |
| 재색인 추가 공간 GiB | 141.1 | 141.1 | 141.1 |
| 독립 백업 공간 GiB | 339.8 | 397.3 | 512.3 |
| 여유 포함 전체 논리 할당 GiB | 1,172.2 | 1,336.6 | 1,665.2 |

개정 보유 계수 1.3, 재색인 1세트, 전체 백업 1세트, 빈 공간 30% 반영. 오브젝트 스토리지 물리 복제/EC, WAL·compaction 임시공간, 대화·감사 로그, 장기 성장, 파서 임시공간은 별도. 질의 복제본 수는 저장소 전체 복제 배수가 아니다. 새 인덱스까지 동시에 load하면 RAM도 추가로 필요하다. 키워드 색인은 서비스 전체 용량 기준으로 포함했으며 기존 G-HeSS API 재사용 시 신규 할당분과 분리한다.

## 3. 전체 재처리 참고 및 증분 적재

현재 문서는 이미 파싱·OCR·임베딩 적재됨. 다음 표는 동일 규모를 전부 다시 처리할 경우의 비교값으로, 즉시 재적재를 권고하는 일정이 아니다. DeDRM은 완료됐으므로 처리 시간에서 제외. 하루 배치 14시간, 효율 70% 가정. VLM 판독·문서 요약은 제외.

| 단계별 유효 경과 시간 | 작은 문서 | 기준 | 큰 문서 |
|---|---:|---:|---:|
| 원본 읽기 (시간) | 0.8 | 0.8 | 0.8 |
| 본문 파싱 (시간) | 6.1 | 12.1 | 24.2 |
| OCR (시간) | 18.2 | 36.3 | 72.6 |
| 임베딩 (시간) | 75.3 | 75.3 | 75.3 |
| 색인 쓰기 (시간) | 6.0 | 6.0 | 6.0 |
| 완전 중첩 시 최소 배치일 | 5.4 | 5.4 | 5.4 |
| 완전 직렬 처리 환산 배치일 | 7.6 | 9.3 | 12.8 |
| 임베딩 입력 토큰 | 3,034,174,400 | 3,034,174,400 | 3,034,174,400 |
| 일 300건 증분의 병목 단계 시간 | 0.37 | 0.37 | 0.37 |

중첩 최소값은 계획 하한이고 직렬 환산값은 비교 기준이다. 실제 완료 기간의 신뢰구간이나 보장 범위가 아니다. 큐 대기, 파일별 편차, 수동 검수, 야간 쿼터, 단계 간 경쟁에 따라 더 길어질 수 있다. OCR의 페이지 비율은 현재 이미지 개수·처리 시간의 대용값이다. 실측 이미지 단위 처리량으로 보정해야 한다.
